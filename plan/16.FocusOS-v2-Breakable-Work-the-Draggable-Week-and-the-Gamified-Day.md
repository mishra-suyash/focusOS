# FocusOS v2 — Breakable work, a draggable week, and a day that prompts you through itself

**Status:** Draft for review
**Routes touched:** `/plan/week` (Steps 2–5, plus one new step), `/plan/day`, `/dashboard`, `/tasks`, `/courses`, `/settings`, `/settings/features`, plus `lib/timeline.ts`, `lib/weekplan.ts`, `lib/courses.ts`, `lib/tracking.ts`, `lib/next-action.ts`, `lib/floating-widget.ts`, `lib/admin-recurring-tasks.ts`, `components/focus-session-provider.tsx`, `components/floating-widget-content.tsx`, `components/plan/time-grid.tsx`
**Companion to:** `14.FocusOS-v2-Weekly-Loop-and-Automatic-Tracking.md` (the weekly loop this doc reworks) and `15.FocusOS-v2-Days-Off-and-Smarter-Weekly-Placement.md` (whose placement pass this doc's chunking feeds candidates into). Also amends `08.FocusOS-v2-Floating-Widget-Plan.md` — see §5.7, which states exactly which of that doc's rules survive and which one this doc narrows.
**Principle carried over:** additive and non-destructive at the data layer — every new field optional, no migration, same rule `14` §1 and `15` §1 set. `15` §1's "no new collection" rule is honored too: nothing here introduces a collection, and §5.1 explains why the breakable-work unit deliberately isn't one.

**Evidence basis:** every current-state claim in §2 is grounded in direct source reads of this repository at commit `df6b478` (HEAD at the time of writing), with file and line references given. No claim here rests on a plan document describing intended behavior — where a plan doc is cited it is cited as *intent*, and the code is cited separately for what actually happens. §7 splits acceptance criteria into the ones a pure-function `scripts/verify-*.ts` can settle and the ones that can only be confirmed in the running app, because the subjects of this doc (drag, timer arming, Picture-in-Picture rendering, notification delivery) are exactly the kind of seam that a green verify script says nothing about.

## 0. TL;DR

The brief, verbatim:

> tasks can be breakable, cant schedule a big chunk and that should be tracked accross the session. once planned map it with focus timers, gamify it
>
> in weekly planning tasks should be draggable with specified objectives (paper reading, revision, assignment for courses etc etc). detach all the other course related things from timeline(it should serve as context for making decision for next week planning. ie show all the upcomming things, then user will specify the time, give text boxes can be prefilled with tentative times)
>
> I want this app to gamify the day, the pip should give prompt notifications what to do next

Five asks, one loop: **plan the week → break work into sittings → start a timer against a sitting → have the leftover roll forward → be prompted through the day.** They are specified together in one doc because the value is entirely in the seams between them, and every one of those seams is currently broken or missing:

1. **Course buckets already chunk; tasks don't.** `placeProposals`' candidates for a course bucket are generated as `Math.round(remaining / workMinutes)` separate chunks (`app/(app)/plan/week/page.tsx:279`, `:299`, `:324`). A task goes through `taskBlockMinutes` (`lib/timeline.ts:224-226`), which is `Math.max(25, estimatedPomodoros × workMinutes)` with **no upper bound** — a 14-pomodoro task becomes one 350-minute block that `placeInWindow` then cannot fit inside a 9-hour working window at all, so it lands under "Didn't fit" and is silently never scheduled. §2.1.
2. **Nothing survives being accepted.** `acceptProposals` writes proposals as bare `ScheduleSlot`s (`app/(app)/plan/week/page.tsx:415-425`) carrying only `courseId`/`bucket`/`assignedTaskIds` — `refType`/`refId` are dropped on the floor. So an accepted "Prep: Midterm" block has no link to its checkpoint, an accepted "Read: X" block has no link to its paper, and `scheduledMinutesThisWeek` (`lib/courses.ts:128-136`) — the function that decides how much more to propose — counts *tasks due this week*, never accepted blocks, so re-opening Step 4 regenerates the same work. §2.2.
3. **The weekly planner is not a planning surface.** Step 4 is an accept/dismiss list grouped by date (`app/(app)/plan/week/page.tsx:783-820`). There is no grid, no drag, no way to say "not there, here." Drag exists only on `/plan/day` (`components/plan/plan-tray.tsx` + `components/plan/time-grid.tsx`, pointer-capture based). §2.3.
4. **The timer ignores the block it was started from.** `startFocus` accepts `slotId`/`taskId`/`courseId`/`bucket` and then sets its length from settings regardless: `const freshTotalSeconds = work * 60` (`components/focus-session-provider.tsx:449`). A 50-minute chunk arms a 25-minute timer. And task credit is counted in *sessions*, not minutes, behind a 5-minute floor (`:419-422`), so "how much of this is left" is not a number the app can state. §2.4.
5. **There is no gamification and the PiP is forbidden from prompting.** The only game-shaped things in the codebase are two streak functions (`lib/analytics.ts:16-25`, `lib/loadindex.ts:122-129`). The floating widget has exactly four items (`lib/floating-widget.ts:7`) and its own source comment says it is "never a generic reminders feed or motivational text (plan §3, §12)" (`components/floating-widget-content.tsx:13-19`) — a rule this doc must confront rather than quietly break. §2.6, §5.6, §5.7.

The through-line of the fix is one idea: **a sitting is a first-class thing.** A task or a bucket target is *work*; a block on a day is *a sitting at that work*; the leftover is derived from real logged minutes, never stored. Once sittings exist, chunking, timer arming, roll-forward, progress, and "what to do next" are all readouts of the same two numbers, and gamification has something honest to count.

## 1. Goals, non-goals, and the assumptions this doc makes explicit

**Goals**

- No block longer than a configured maximum sitting ever gets proposed or created by the planner. Work that exceeds it is split into sittings, each placed separately, each labeled *n of m*.
- What is left of a piece of work is a *derived* number in real minutes, computed from `PomodoroSession.minutes` actually logged against it — not a session count, not `estimatedPomodoros − completedPomodoros`. A sitting that ran 20 of its 50 minutes leaves 30 minutes that show up in the next sitting and in the next week's planning.
- Every block carries an **objective** — what it is *for* — and that objective survives being accepted onto a day, is visible on the timeline, and is what the focus timer attributes its session to.
- Weekly planning is a surface you can *plan on*: a week grid where a proposed sitting can be dragged to a different day and time, with a full keyboard/click equivalent for every drag (WCAG 2.5.7, the standard `components/plan/plan-tray.tsx:403-411` already holds itself to).
- Derived course work stops being written onto the day timeline behind the user's back. The timeline shows what is genuinely fixed (lectures, routine, external calendar) plus what the user has confirmed. Everything else appears in weekly planning as **upcoming context** with a **prefilled tentative time the user confirms or edits**.
- The day has a score, a streak, and a visible count of sittings closed, all derived from real logged data.
- The floating Picture-in-Picture window tells you what to do next, and can optionally raise a system notification at a sitting boundary.

**Non-goals**

- **No new Firestore collection**, per `15` §1. §5.1 explains why a sitting is a field on an existing document rather than a `workChunks` collection, and §8 records the case for changing that later.
- **No points economy.** No currency, no purchasable rewards, no levels with invented names, no loss framing ("you broke your streak!"), no confetti as the reward for its own sake. §5.6 defines gamification as *a readout of numbers the app already measures*, and §8 flags levels/badges as a genuine product decision rather than assuming them.
- **No AI in this pass.** Chunk splitting, objective inference, and tentative-time prefills are all deterministic. Same reason `14` §1 and `15` §5.4 give: no feature is AI-only, and none of these are creativity problems.
- **No general scheduler rewrite.** `placeProposals` (`lib/weekplan.ts:201-271`) keeps its `15`-era structure — exclusions, preferred days, per-`capGroup` caps. This doc changes *what candidates it is handed* (many small sittings instead of one huge block) and *what a placed candidate turns into*, not how it searches.
- **No cross-midnight sittings**, no multi-day blocks. `lib/timeline.ts`'s `clampToDay` invariant stands.
- **Not removing class blocks from the timeline.** See the assumption below — this is the single most consequential reading in the doc.
- **One deliberate exception to "additive and non-destructive," named rather than buried:** §5.4 stops `syncRevisionTemplate` (`lib/courses.ts:70-83`) from auto-creating a course's revision commitment. That is a behavior *removal*, the only one in this doc, and it has a cost — it makes weekly planning the only path by which a revision target becomes scheduled work. §5.4 states that trade in full and §8 Q8 asks whether it is the right call. No data is deleted: existing generated templates are paused-able, never removed.

**Assumptions this doc makes explicit, rather than blocking on**

- **A1 — "detach all the other course related things from timeline" means the *derived* course work, not lectures.** A `CourseSession` materialized by `courseSlotsForDate` (`lib/courses.ts:15-40`) is a real, externally-fixed event; removing it would leave the timeline lying about the day. What gets detached is course work the app *invented*: Step 4's auto-placed revision/assignment/backlog blocks, and the auto-generated revision commitment that `syncRevisionTemplate` (`lib/courses.ts:70-83`) quietly creates and keeps in sync with a course's `targetMinutesPerWeek`. Those stop landing on a day until the user has confirmed a time for them. §5.4 specifies this; §8 Q1 records the stronger reading (lectures move to a separate lane too) in case that is what was meant.
- **A2 — "specified objectives" is a view over the three taxonomies that already exist, not a fourth one.** `TaskBucket` (`goal`/`assignment`/`backlog`/`revision`), `Category`, and `ScheduleSlotType` all already exist and already overlap. "Paper reading" is not a `TaskBucket`; it is `ScheduleSlotType: "reading"` plus a paper reference. §5.2 defines an objective as a *derivation* over fields a slot already carries plus one new optional reference field — not a new enum competing with `TaskBucket`.
- **A3 — "pip should give prompt notifications" means two distinct mechanisms**, and this doc specifies both separately because they have completely different constraints: an in-PiP "next up" card (Chromium-only, no permission, renders whatever `pickNextAction` already computes) and an OS-level `Notification` (needs explicit permission, must be fired from the main document, opt-in, default off). §5.7.
- **A4 — "tracked across the session" is read as "across sittings", i.e. the leftover rolls forward.** The other available reading — "tracked within a single focus session" — is already true (`PomodoroSession.minutes` is real elapsed time, `lib/tracking.ts`'s `slotCoverageMinutes` already sums it per block). The thing that does not exist is the roll-forward, so that is what §5.1 builds.

**What carries over unchanged**

`15`'s day-off exclusion, per-`capGroup` caps, preferred days, and lead-time spreading all stay exactly as they are and are *fed by* this doc's chunking. `14`'s `WeekPlan` shape, the `weeklyPlanning` anchor, `slotAutoStatus`'s 60% coverage rule, and automatic course attribution via `ScheduleSlot.courseId`/`bucket` all stay. The `Day` document stays the single per-date read. The one thing from `14` that does **not** carry over unchanged is its auto-generated revision commitment — see the non-goal above and §5.4.

## 2. What's broken today, with receipts

### 2.1 A task is never broken into sittings, and a big one is therefore never scheduled at all

Two code paths size work for the planner, and they disagree.

Course buckets are chunked. From `app/(app)/plan/week/page.tsx:277-291` (assignment; `:296-311` revision and `:321-335` backlog are identical in shape):

```ts
const target = hoursFor(course, "assignment");
const alreadyScheduled = scheduledMinutesThisWeek(tasks, course.id, "assignment", workMinutes, weekDateKeys);
const chunks = Math.round(Math.max(0, target - alreadyScheduled) / workMinutes);
for (let i = 0; i < chunks; i += 1) {
  candidates.push({ /* one candidate of `workMinutes` each */ });
}
```

A 3-hour revision target becomes seven 25-minute candidates, each placed independently. That is chunking, and it works.

Tasks are not chunked. From `app/(app)/plan/week/page.tsx:337-348`:

```ts
const duration = taskBlockMinutes(task, workMinutes);
```

and `lib/timeline.ts:224-226`:

```ts
export function taskBlockMinutes(task: Pick<Task, "estimatedPomodoros">, workMinutes: number): number {
  return Math.max(25, (task.estimatedPomodoros ?? 1) * workMinutes);
}
```

There is a floor and no ceiling. With the default `workMinutes` of 25 (`app/(app)/plan/week/page.tsx:99`), a task estimated at 14 pomodoros yields a single 350-minute candidate. `placeInWindow` (`lib/weekplan.ts:112-130`) opens with:

```ts
if (durationMinutes > windowEnd - windowStart) return null;
```

Against the default working window of 09:00–18:00 (`DEFAULT_WORKING_WINDOW`, `lib/weekplan.ts:8-12`) that is 540 minutes, so 350 technically fits the bound — but it needs 350 contiguous free minutes on some single day, and any day with a lunch routine block in the middle of it has none. `placeProposals` returns `fits: false` (`lib/weekplan.ts:269`), the week page files it under "Didn't fit" with the message "no free gap of 350m inside the working window" (`app/(app)/plan/week/page.tsx:822-834`), and the task is never scheduled. The user sees a red row and no route forward: there is no "split it" control, because splitting is not a concept the code has.

The same function is the sizer for the drag-and-drop path (`createTaskBlock`, `lib/timeline.ts:326-341`) and for the dashboard's "Schedule it" (`app/(app)/dashboard/page.tsx:146-149`), so the uncapped duration is not confined to the weekly planner.

There is one more sizing path, and it drops information outright. `RecurringTaskTemplate` carries an optional fixed clock time (`types/index.ts:370`: `time?: { startTime: string; endTime: string; location?: string }`) — that is how a weekly TA meeting or fixed office hour is expressed. But `taskFromTemplate` (`lib/admin-recurring-tasks.ts:16-29`) copies nine fields onto the generated `Task` and **`time` is not among them**; `Task` has no field to receive it. So a commitment the user gave a specific clock time to materializes as a timeless task, and when the weekly planner later picks it up as a backlog task it sizes it with `taskBlockMinutes` and places it wherever the search finds room — at an unrelated time, at the generic default length.

### 2.2 An accepted proposal loses its identity, so nothing can be tracked across sittings

`acceptProposals` (`app/(app)/plan/week/page.tsx:401-453`) turns each accepted `WeekProposal` into a `ScheduleSlot`. The whole mapping, `:415-425`:

```ts
const newSlots: ScheduleSlot[] = props.map((p) => ({
  id: crypto.randomUUID(),
  title: p.title,
  type: p.type,
  startTime: p.startTime,
  endTime: p.endTime,
  status: "upcoming",
  ...(p.courseId ? { courseId: p.courseId } : {}),
  ...(p.bucket ? { bucket: p.bucket } : {}),
  ...(p.taskId ? { assignedTaskIds: [p.taskId] } : {})
}));
```

`WeekProposalCandidate` also carries `refType?: "checkpoint" | "revision"` and `refId?: string` (`lib/weekplan.ts:148-149`), which is how checkpoint prep and revision-queue candidates identify themselves. **Neither is copied.** `ScheduleSlot` (`types/index.ts:207-231`) has no field to copy them into. Consequences, all three real:

- An accepted "Prep: Midterm" block cannot be traced back to its `Checkpoint`. The block is a string.
- A stale-paper reading proposal carries its paper id in `refId` (`app/(app)/plan/week/page.tsx:357`, `:359`) and loses it on accept, so the accepted block cannot open the paper, cannot pre-arm the pass timer, and cannot credit the paper's progress.
- Per-day chunk identity does not exist at all. Seven 25-minute "CS201 — Revision" blocks accepted across a week are seven unrelated slots with identical titles. Nothing says which is *2 of 7*, nothing ties them together, and nothing knows the set was one 3-hour intention.

The second half of the problem is the counting. `scheduledMinutesThisWeek` (`lib/courses.ts:128-136`) is what Step 4 subtracts from a bucket target before deciding how many chunks to propose:

```ts
function tasksDueThisWeek(tasks, courseId, bucket, weekDateKeys) {
  return tasks.filter((task) => task.courseId === courseId && task.bucket === bucket && task.dueDate && weekDateKeys.includes(task.dueDate));
}
```

It counts **tasks**. Accepted proposals are **slots**. So accepting every one of a bucket's proposals does not reduce `alreadyScheduled` by a single minute, and re-deriving Step 4 proposes the identical set again. The only thing that stops a re-offer is `blockDecisions`, keyed by the candidate's *array index* — `const key = \`${index}\`` (`lib/weekplan.ts:244`), read back at `app/(app)/plan/week/page.tsx:795`. Add a course, change a target, mark a day off, or finish a task, and the candidate list shifts; every stored decision then applies to a different proposal than the one it was made about.

The primitive for honest progress does exist for tasks, and it is already documented as derived-never-stored (`types/index.ts:174-175`). It is just counted in the wrong unit. `finalizeSession` (`components/focus-session-provider.tsx:409-438`) credits a task like this, `:419-422`:

```ts
const MIN_MINUTES_FOR_TASK_CREDIT = 5;
if (data.mode === "work" && data.taskId && data.minutes >= MIN_MINUTES_FOR_TASK_CREDIT) {
  await incrementTaskCompletedPomodoros(user!.uid, data.taskId);
}
```

One increment per session over 5 minutes. A 6-minute session and a 50-minute session advance a task by exactly the same amount — the precise mistake `14` §6.4 already fixed for *course* totals by switching them to real `PomodoroSession.minutes` (see `completedMinutesThisWeek`, `lib/courses.ts:148-166`, whose own doc comment calls this out). Tasks never got that fix. So `components/task-list.tsx:80-81` renders "2 of 6 focus sessions · 4 left" from a count that may represent anywhere from 10 minutes of work to two hours.

### 2.3 Weekly planning has no grid, no drag, and no way to say "not there"

Step 4's entire interaction surface (`app/(app)/plan/week/page.tsx:783-820`) is: group fitting proposals by date, print each as a text row of `startTime–endTime · title`, and offer **Accept**, **Dismiss**, and a per-day **Accept day**. The time on each row is whatever `placeProposals` chose. There is no input to change it, no grid to drop it on, and no way to move it to another day short of dismissing it and hand-building a block on `/plan/day`.

Meanwhile the app already owns a complete, accessibility-reviewed drag implementation — on the *other* route. `components/plan/time-grid.tsx` (28KB) handles pointer capture, snap, magnetism, ripple, and lane layout; `components/plan/plan-tray.tsx` (24KB) supplies draggable task/quick-block/template sources. That machinery is per-day. The week planner cannot reuse it as-is (it is a single-day grid) and currently reuses none of it.

That tray also establishes the accessibility standard any new drag surface inherits — `components/plan/plan-tray.tsx:403-405`:

```
// Keyboard activation never goes through pointerdown/up, so this can't double-fire
// alongside the drag path below — it's the WCAG 2.5.7 non-drag equivalent (§9).
```

Every draggable thing in the tray has a dedicated button doing the same job without a pointer gesture. A week grid must ship the same way, and §5.3 specifies it.

### 2.4 The focus timer knows which block it is in and ignores it

`startFocus` (`components/focus-session-provider.tsx:441-453`) takes exactly the context needed to arm a sitting — and then does not use it for length:

```ts
function startFocus(opts: { label: string; category: Category; slotId?: string; taskId?: string; courseId?: string; bucket?: TaskBucket }) {
  setLabel(opts.label);
  setCategory(opts.category);
  setSlotId(opts.slotId);
  setTaskId(opts.taskId ?? "");
  setCourseId(opts.courseId);
  setBucket(opts.bucket);
  setMode("work");
  const freshTotalSeconds = work * 60;   // :449 — settings length, unconditionally
  ...
}
```

`work` is the user's configured work length (`:165`, seeded from `UserSettings.workMinutes`). So a 50-minute chunk on the timeline arms a 25-minute timer, the sitting ends half-covered, and `slotAutoStatus`'s 60%-coverage rule (`lib/tracking.ts:50-60`) leaves the block un-completed — correctly, but for a reason the user never chose.

`14` §6.2's intent ("the timer reads the block you are in") is *partially* real: attribution works (`slotId`, `courseId`, `bucket` all flow through to `PomodoroSession`, `types/index.ts:186-205`), and `NextAction.slot` exists precisely so a card can pre-arm the timer (`lib/next-action.ts:15-18`). Duration is the one thing that did not come along.

### 2.5 The timeline is written to by machinery the user did not point at a day

Three mechanisms put course-derived content onto a day without the user choosing a time for it:

1. **Step 4 accept** — `acceptProposals` writes straight to `saveDailySchedule` (`app/(app)/plan/week/page.tsx:434`), at times the placement search picked. Two bulk buttons make that a single gesture: "Accept all" (`:756-758`) accepts every proposal for the whole week, and "Accept day" (`:791`) accepts one day's worth.
2. **`syncRevisionTemplate`** (`lib/courses.ts:70-83`) creates and maintains a `RecurringTaskTemplate` with `generatedFrom: "courseRevisionTarget"` from a course's `targetMinutesPerWeek`. Its instances become real `Task` docs on a rolling window via the cron at `app/api/cron/recurring-tasks/route.ts`, and then flow into the planner as ordinary tasks.
3. **`mergeMissingLockedSlots`** (`lib/schedule.ts:121`) materializes class blocks, routine blocks, and the weekly-planning anchor into every day at three call sites (`components/plan/day-timeline-editor.tsx:126`, `:311`, `:371`).

Of the three, only (3) is materializing genuinely fixed reality, and only (3) should keep doing it silently. (1) and (2) are the app deciding *when* the user will do course work. Meanwhile `/plan/week` Step 2, "The week already contains" (`app/(app)/plan/week/page.tsx:620-670`), already assembles very nearly the right context panel — per-day chips for the weekly-planning anchor, classes, routine, recurring commitments, checkpoints due, and external calendar events. It is read-only and it stops at that week's *fixed* content: it does not list what is *coming* (next week's checkpoints, assignment due dates, goal milestones, the revision queue's depth, stale papers), and it offers no time input on anything.

### 2.6 There is no gamification, and the PiP's own charter forbids the thing being asked for

Search across `lib/`, `components/`, and `types/` for `xp`, `streak`, `gamif`, `badge`, `reward`, `level` turns up: `calculateStreak` (`lib/analytics.ts:16-25`, consecutive days with any session), `computeLoadIndexStreak` (`lib/loadindex.ts:122-129`, consecutive days at Load Index ≥ 0.9), the `onTrackStreak` copy entry (`lib/copy.ts:22`), and `meterLevel` in the admin panel. Nothing else. No score, no per-day sense of completion, nothing that counts sittings.

The floating widget is fixed at four items (`lib/floating-widget.ts:7`):

```ts
export type FloatingWidgetItemId = "timer" | "currentFocus" | "hydrationNudge" | "loadIndex";
```

and both its files carry the same explicit prohibition. `lib/floating-widget.ts:1-7`: "Deliberately not a generic 'pin anything' framework … each item picked because it's glanceable (a number/progress bar, not prose) and single-tap actionable." `components/floating-widget-content.tsx:13-19`: "never a generic reminders feed or motivational text (plan §3, §12)." A third repeat sits inline at `:72`.

So "gamify it" and "the pip should give prompt notifications" land directly on a rule an earlier plan set on purpose. §5.6 and §5.7 take that seriously: the *tests* plan/08 set — glanceable, single-tap actionable, a number not prose — are good tests, and everything this doc adds to the widget passes them. What this doc narrows is the blanket ban on "motivational text," and it says so in the open rather than shipping around it.

## 3. Scenarios

### S1 — A 6-hour task gets broken up instead of vanishing

A task, "Write related-work section," estimated 14 pomodoros. Today Step 4 shows it in red: *no free gap of 350m inside the working window*. After this doc: Step 4 shows **seven** rows, "Write related-work section (1 of 7)" through "(7 of 7)", 50 minutes each, spread across the week by `15`'s placement pass with its per-`capGroup` cap keeping them off one day. Each row is a real sitting with its own time. → §5.1, §5.3

### S2 — Monday's sitting runs short; Wednesday's knows

Monday's 50-minute sitting at that task. The timer arms at **50** minutes, not 25, because the block says 50. Twenty-two minutes in, an interruption; Finish. The session logs 22 real minutes. The block does not flip to completed (22/50 is under the 60% rule) and that is right. Wednesday's sitting card now reads *"2 of 7 · 28 min carried over from Mon"* and arms a 78-minute sitting — or, if that exceeds the maximum sitting length, arms 50 and the remainder goes back into the pool for the next planning pass. Nothing was lost, and nothing was fabricated: the numbers are `sum(PomodoroSession.minutes where taskId = …)` against the task's own total. → §5.1, §5.5

### S3 — Dragging a sitting to a better day

Step 4's week grid shows seven columns, the working window on the vertical axis, fixed content (lectures, routine, weekly-planning anchor, external calendar) drawn locked, and proposed sittings drawn as movable blocks. Thursday afternoon is the wrong time for "CS201 — Revision (3 of 7)" — a long lab drains that day. Dragging it to Wednesday 16:00; it snaps to 15-minute increments, refuses to overlap the lecture already there, and the capacity readout updates. No mouse: Tab to the block, press Enter to open its inspector, change the day from a `<select>` and the time from a typed `HH:mm` field — the same non-drag equivalent `plan-tray.tsx` already holds itself to. → §5.3

### S4 — Every block says what it is for

The revision sitting shows **Revision · CS201**. The prep sitting shows **Prep · Midterm 1** and links to the checkpoint. The reading sitting shows **Paper reading · "Attention Is All You Need" · Pass 2** and opens the paper. Starting a timer inside any of them attributes the session to exactly that objective with no dropdown touched, because the objective reference now survives the accept. → §5.2

### S5 — Upcoming becomes context, and the user sets the time

Sunday, `/plan/week`. A new step between "The week already contains" and "Set this week's hours": **What's coming**. One row per real, dated thing in the next 14 days — checkpoints, assignment due dates, goal milestones, external-deadline tasks, the revision queue's depth, papers stale 14+ days — each with an estimate and a **tentative day and time already filled in** (derived: lead time back from the deadline, the course's own lecture day for revision, the weekend for leftovers — `15` §5.2's preferences, now surfaced as an editable suggestion instead of an invisible one). Accepting a row as-is takes one click. Editing the time first takes one edit. Nothing lands on a day until a row is accepted, so the timeline stops filling with times the user never chose. → §5.4

### S6 — The day keeps score, honestly

The dashboard shows *Today: 4 of 6 sittings closed · 185 of 260 planned minutes · on-track streak 6d*. Every number is derived: sittings closed from `slotAutoStatus` over the day's blocks, minutes from real `PomodoroSession.minutes`, the streak from the existing `computeLoadIndexStreak`. Marking a day off (per `15` §5.1) does not break the streak. No points, no badge, no confetti-for-its-own-sake. → §5.6

### S7 — The PiP says what's next

The PiP window gains a fifth card: **Next up — CS201 Revision (3 of 7), 16:00, starts in 12 min**, with one button, *Start*, which arms the timer at that sitting's length and attributes it to that sitting's objective. It is rendering `pickNextAction`'s existing output; the cascade already has a "starts within 15 minutes" branch (`lib/next-action.ts:83-95`). Separately, and only if the user has explicitly granted permission in Settings, one system notification fires when a sitting is about to start and one when it ends. → §5.7

## 4. Data model changes

Eight additive optional fields and one new derived type. No collection, no migration; absent means today's behavior in every case, the convention `14` and `15` both set.

```ts
// types/index.ts — ScheduleSlot, additive

/** plan/16 §5.2 — what a block is FOR, in a form that survives being accepted onto a day.

 *  cases it never covered, and — unlike today, where acceptProposals drops both (§2.2) — is
 *  actually copied onto the slot. `courseId`/`bucket` stay the carriers for course work; this is
 *  for the objectives that aren't a course bucket. */
export type SlotObjectiveRef =
  | { kind: "checkpoint"; id: string }
  | { kind: "paper"; id: string; passNo?: 1 | 2 | 3 }

  | { kind: "revisionQueue" };

   *  logged minutes (§5.1). Absent = an ordinary single block, unchanged. */
  chunk?: { groupId: string; index: number; total: number };
  /** plan/16 §5.1 — minutes this sitting was *planned* to contribute, as distinct from
   *  `endTime - startTime`. Normally identical; they diverge when a sitting is resized on the

  plannedMinutes?: number;

// types/index.ts — Task, additive

export interface Task {
  // ...existing fields unchanged...
```

**Deliberately not added:** a stored `remainingMinutes`, on either a task or a slot. It is always derived (§5.1). Two copies of "how much is left" is exactly the drift `types/index.ts:174` already warns about for `completedPomodoros`, and `14` §6.4 already had to fix one instance of it.

## 5. Design

### 5.1 Breakable work: the split, and the leftover that rolls forward

Three pure functions in `lib/timeline.ts` (splitting) and `lib/tracking.ts` (progress). No I/O, no React, so all of §7's splitting and progress criteria are settleable by a verify script.

**The split.** Replaces the unbounded `taskBlockMinutes` at every call site:

```ts
export const DEFAULT_MAX_CHUNK_MINUTES = 50;
export const DEFAULT_MIN_CHUNK_MINUTES = 15;

/** plan/16 §5.1 — splits `totalMinutes` into sittings of at most `maxChunkMinutes`, none shorter
 *  than `minChunkMinutes`. Returns one element for work that already fits, and a single-element
 *  array for unsplittable work regardless of length (the caller then gets `fits: false` from
 *  placement if it truly cannot be placed — a deliberate refusal, not a silent split of something
 *  the user said must happen in one sitting). Sittings are equal-sized rather than
 *  "max, max, max, remainder": `Math.ceil(total / max)` sittings of `Math.ceil(total / count)`
 *  each, so 120 minutes at a 50-minute cap gives 3x40, not 50+50+20 — a trailing stub is both
 *  harder to place and less useful than three even sittings. */
export function splitIntoChunks(
  totalMinutes: number,
  opts: { maxChunkMinutes?: number; minChunkMinutes?: number; splittable?: boolean }
): number[];
```

Worked: 350 minutes, 50-minute cap → `ceil(350/50)` = 7 sittings of `ceil(350/7)` = 50 each. 120 at a 50 cap → 3 sittings of 40. 55 at a 50 cap → 2 of 28 (not 50+5, which the 15-minute floor rejects). 30 at a 50 cap → one of 30. Unsplittable 350 → one of 350.

Call sites, all of which currently share the uncapped sizer:

- `app/(app)/plan/week/page.tsx:337-348` — backlog tasks. Each element becomes its own candidate carrying `chunk: { groupId, index, total }`, all sharing one `capGroup` per task (`task:<id>`) so `15`'s per-group cap keeps one task's sittings from stacking on one day. A task with a `weeklyTargetDay` keeps `leadTimeCandidates`' lead-time spreading, now fed the split rather than one lump.
- `createTaskBlock` (`lib/timeline.ts:326-341`) and the dashboard's "Schedule it" (`app/(app)/dashboard/page.tsx:146-149`) — place the *first* sitting at the chosen gap and report "1 of n scheduled; n-1 to plan," rather than dropping one giant block. Dropping work larger than one sitting onto a day is the one interaction where a silent split would be surprising, so it is explicit.
- `planRevisionTemplateSync` (`lib/recurring-tasks.ts:93`) already documents itself as the inverse of `taskBlockMinutes`; it inherits the cap so a generated revision commitment stops being able to exceed one sitting.
- Course-bucket candidates (`:277`, `:296`, `:321`) switch from `workMinutes`-sized chunks to `splitIntoChunks(remaining, …)`. This is a behavior change worth naming: a 3-hour revision target currently becomes seven 25-minute sittings; with a 50-minute cap it becomes four 45-minute ones. Fewer, longer sittings is the intent — 25 minutes is a *timer* default, never a considered statement about how long a block of revision should be.

**The leftover.** One function, minutes not counts:

```ts
/** plan/16 §5.1 — minutes still owed on a piece of work: its planned total minus real logged
 *  session minutes. Deliberately minutes, not `estimatedPomodoros - completedPomodoros`: that
 *  counter advances once per session over 5 minutes (components/focus-session-provider.tsx:419-422),
 *  so a 6-minute session and a 50-minute one move it identically — the same defect plan/14 §6.4
 *  already fixed for course totals by switching them to real `PomodoroSession.minutes`, never
 *  applied to tasks. Clamped at 0; a task worked past its estimate owes nothing, it does not owe
 *  negative time. */
export function remainingMinutes(
  work: { totalMinutes: number },
  sessions: Pick<PomodoroSession, "mode" | "minutes" | "taskId">[],
  workId: string
): number;
```

`totalMinutes` for a task is `(estimatedPomodoros ?? 1) × workMinutes` — the same arithmetic as today, now named and used consistently. Progress is therefore never stored and never drifts, and S2's "28 min carried over from Mon" is a subtraction over data that already exists.

`Task.completedPomodoros` and the 5-minute floor stay exactly as they are. `components/task-list.tsx:80-81` keeps rendering the session count, which is a genuinely useful "how many times have I sat with this" number; it gains a minutes line beside it. Nothing is removed — the minutes figure is added as the one the planner reads.

**Why no `workChunks` collection.** A sitting is a `ScheduleSlot` on a `DailySchedule`, which is already loaded for every day the planner and the timeline touch. A collection would mean a second query per week, a second write per accept, a second thing to keep consistent with the slot that represents it, and a migration. The cost is real and named in §8 Q3: with sittings living on slots, "what is left of this task" requires reading the week's schedules plus the week's sessions, so it is a client-side derivation over data the page already has rather than a single indexed query. That is fine for one user's own week and would not be fine at another order of magnitude.

### 5.2 Objectives: a derivation, not a fourth taxonomy

An **objective** answers "what is this block for," and is computed from fields a block already carries plus the new `objectiveRef`:

```ts
export interface Objective {
  /** Short chip text: "Revision", "Assignment", "Paper reading", "Prep", "Spaced repetition". */
  label: string;
  /** Second line, when there is one: the course name, the paper title, the checkpoint title. */
  detail?: string;
  /** Where the chip links. */
  href?: string;
  /** What a focus session started here should attribute to — exactly the shape `startFocus` takes. */
  attribution: { courseId?: string; bucket?: TaskBucket; taskId?: string; paperId?: string; passNo?: 1 | 2 | 3 };
}

export function describeObjective(slot: ScheduleSlot, ctx: { courses: Course[]; papers: Paper[]; checkpoints: Checkpoint[]; tasks: Task[]; goals: Goal[] }): Objective | null;
```

Resolution order, first match wins: `objectiveRef` (the explicit case) → `courseId` + `bucket` (course work, already stored) → `assignedTaskIds[0]` resolving to a task with a `courseId`/`bucket` → `type: "class"` → `type: "reading"` with no reference (generic reading) → `null` for a block that is only what its type says.

This adds no enum. `TaskBucket` remains the four planning buckets, `Category` remains the task taxonomy, `ScheduleSlotType` remains the block taxonomy, and "paper reading" stays what it already is — `type: "reading"` plus a paper reference — rather than becoming a fifth `TaskBucket` member that `bucketWeeklyTarget` (`lib/courses.ts:99-114`) would then have to grow a meaningless branch for.

The fix that makes objectives real is small and lives in `acceptProposals`: extend the `newSlots` map at `app/(app)/plan/week/page.tsx:415-425` to copy `objectiveRef`, `chunk`, and `plannedMinutes`. Candidate generation sets `objectiveRef` where it already knows the reference and merely discards it — `{ kind: "checkpoint", id: cp.id }` at `:269`, `{ kind: "revisionQueue" }` at `:315`, `{ kind: "paper", id: paper.id }` at `:357`/`:359`.

Objectives then render in four places, all reading the one function: the week grid (§5.3), the day timeline's block and its inspector (`components/plan/block-inspector.tsx`), the Now card (`components/now-card.tsx`), and the PiP's next-up card (§5.7).

### 5.3 A week grid you can plan on

Step 4 becomes a seven-column grid: days across, the working window (`UserSettings.workingWindow`, defaulting to 09:00–18:00) down. Day-off dates render as struck-through columns that accept nothing, per `15` §5.1. Three layers per column:

1. **Fixed** — lectures, routine blocks, the weekly-planning anchor, external calendar events, and any already-saved schedule. Drawn locked; the same set Step 2 already assembles at `app/(app)/plan/week/page.tsx:620-670` and the same set `claimedSlotsForDate` (`:148-158`) already feeds to the capacity meter and the placement search. No new data source.
2. **Proposed sittings** — movable, each showing its objective chip and its "n of m".
3. **A drop shadow** while dragging, refusing any position that overlaps layer 1 or another proposal.

Reuse, not a rewrite: the geometry helpers in `lib/timeline.ts` (`minutesToPx`, `pxToMinutes`, `snapMinutes`, `magnetize`, `clampToDay`, `rangeOverlapsSlots`) are already pure and already day-agnostic. A week grid is seven columns each doing what `time-grid.tsx` does for one, so the new component is a layout shell over those helpers plus one addition: a horizontal hit test mapping x to a date key. `placeInWindow`'s 15-minute step sets the snap increment so a dragged position is always one the placement search could itself have produced.

**Non-drag equivalent, mandatory.** Every proposal row keeps its text form and gains an inspector reachable by keyboard: a day `<select>` (the seven dates, day-off dates disabled), a typed `HH:mm` start using the existing `components/plan/typed-time-input.tsx`, a duration field, and Accept/Dismiss. This is the same standard `plan-tray.tsx:403-405` holds itself to, and it is also the fallback for narrow screens where a seven-column grid does not fit. The grid is the enhancement; the list is the floor.

**Moving a proposal writes nothing until Accept.** A moved proposal updates local state and the capacity readout only. `WeekPlan.proposedBlocks` is a Firestore array field — a `merge: true` write replaces it wholesale (`types/index.ts:294-296`) — so per-drag persistence would mean rewriting the whole array on every pointer-up. Accept is already the commit point and stays it.

### 5.4 Detaching derived course work, and "What's coming" as the context surface

Per assumption A1: **lectures, routine blocks, the weekly-planning anchor, and external calendar events keep materializing onto the day timeline exactly as they do now** (`mergeMissingLockedSlots`, its three call sites unchanged). They are fixed reality, and `15` and `14` both depend on them being there.

What changes is that **derived course work reaches a day only through an explicit user confirmation**:

- **The two bulk-accept buttons are removed** — "Accept all" (`app/(app)/plan/week/page.tsx:756-758`, which accepts every proposal for the entire week in one click) and "Accept day" (`:791`). Per-proposal Accept stays. One click that writes a whole week of blocks at times nobody looked at is the exact behavior being complained about, and with §5.3's grid there is no longer any reason for it to exist. If a bulk path is still wanted after living with the grid, it should be "accept everything I have already reviewed", not "accept everything".
- **`syncRevisionTemplate` (`lib/courses.ts:70-83`) stops auto-creating the revision commitment.** A course's `targetMinutesPerWeek` stops silently becoming recurring `Task` docs that land on days. The target keeps its real job — it is `bucketWeeklyTarget`'s "revision" input (`lib/courses.ts:99-114`) and therefore drives Step 4's revision proposals, which the user then places. Existing templates with `generatedFrom: "courseRevisionTarget"` are **not** deleted (that would destroy user data without being asked); they are surfaced on `/courses` with a one-line explanation and a control to stop them. `planRevisionTemplateSync`'s `"pause"` branch already exists for precisely this.

  **The cost of this one, stated plainly, because it is the only non-additive change in the doc.** `planRevisionTemplateSync` is currently the *only* mechanism that turns `Course.targetMinutesPerWeek` into scheduled revision work without the user doing anything: the template's instances are generated by the cron at `app/api/cron/recurring-tasks/route.ts` on a rolling window, whether or not `/plan/week` is ever opened. Removing it means **weekly planning becomes mandatory for revision to happen at all** — a user who sets a revision target and never runs the planner gets zero revision work, where today they get tasks. That is a deliberate trade (the passive path is exactly the "course things appearing on the timeline nobody chose" being complained about), but it is a trade, and it is only acceptable if weekly planning is genuinely a habit. Two mitigations belong in Phase 4 rather than being assumed: the `weeklyPlanning` anchor (`14` §5.6) already puts the ritual on the calendar, and `/courses` should say, next to any target with no planned minutes this week, that the target is not scheduled yet. §8 Q8 asks whether the removal is right at all, or whether the auto-template should instead survive as an explicit opt-in per course.
- **A new Step 2.5, "What's coming."** One row per real, dated thing in a configurable horizon (default 14 days), assembled from data the page already loads: checkpoints with `dueAt` and `prepEstimateMin`/`prepLeadDays`; tasks with a `dueDate` in range, `kind: "external"` ones flagged; goal milestones with a `dueAt`; the revision queue's due count and minutes; papers in `reading` untouched 14+ days; each active course's four bucket targets against `completedMinutesThisWeek`. Each row carries **an estimate and a prefilled tentative day and time**, derived exactly as `15` §5.2's preferences already choose one — lead time back from a deadline, the course's own lecture days for revision, the weekend for leftovers — with the difference that the suggestion is now *visible and editable* rather than applied invisibly. Accepting a row generates its candidate(s), split per §5.1, at the confirmed time.

The prefill is the whole point of the ask ("text boxes can be prefilled with tentative times"): the app still does the thinking, and the user still owns the clock.

### 5.5 Mapping sittings to the focus timer

Three changes, all in `components/focus-session-provider.tsx`, none touching the pomodoro cycle or break logic.

**The sitting sets the length.** `startFocus` gains an optional `minutes`:

```ts
function startFocus(opts: {
  label: string; category: Category;
  slotId?: string; taskId?: string; courseId?: string; bucket?: TaskBucket;
  /** plan/16 §5.5 — this sitting's length. Absent = `work` (the settings length), which is every
   *  existing caller's behavior unchanged. Clamped to [minChunkMinutes, maxChunkMinutes] so a
   *  mis-sized block can't arm a two-hour "pomodoro". */
  minutes?: number;
  paperId?: string; passNo?: 1 | 2 | 3;
})
```

Callers that start from a block pass the block's remaining minutes: its `plannedMinutes` (or duration) minus what `slotCoverageMinutes` (`lib/tracking.ts:34-40`) already says is covered, so resuming a partly-covered sitting arms only what is left rather than restarting it. The Now card, the PiP next-up card, and the block inspector all pass it; the manual timer on `/dashboard` does not, and behaves as it does today.

**Attribution covers reading.** `PomodoroSession` already has `paperId` and `passNo` (`types/index.ts:200-201`) for the pass timer; `startFocus` cannot currently set them, so a reading block started from the timeline loses the paper. Threading them through closes that, and `describeObjective`'s `attribution` is exactly the argument shape, so a caller passes one object with no per-case logic.

**Boundary events.** `finalizeSession` already recomputes block status via `syncSlotAutoStatus` (`:426-428`). It gains one call to a pure `sittingOutcome(slot, sessions)` returning `"closed" | "partial" | "untouched"`, which is what the day score (§5.6) counts and what the notification (§5.7) reports. `slotAutoStatus`'s 60% threshold stays the definition of closed — one rule, one place.

### 5.6 Gamification: a readout, not an economy

Everything below is derived from data already stored. No new source of truth, no invented currency.

```ts
/** plan/16 §5.6 — the day's 0-100 score. Three terms, weighted, each already measured elsewhere:
 *   - coverage (50): logged work minutes / planned work minutes, capped at 1. The honest core —
 *     did the day happen as planned.
 *   - closure (30): sittings closed / sittings planned, by `slotAutoStatus`'s own 60% rule. A day
 *     of half-finished sittings scores below a day of finished ones at equal minutes, which is the
 *     behavior worth rewarding.
 *   - consistency (20): 1 when the day's Load Index is in "on_track" or "ahead", scaled down
 *     through "light", 0 at "behind"/"overrun". Reuses `loadIndexBand`, so the score can never
 *     disagree with the Workload number shown right next to it.
 * A day with nothing planned scores `null`, not 0 — an unplanned day is not a failed one, the same
 * distinction plan/15 §5.1 drew for days off (`computeRequiredMinutes` returns 0 rather than
 * reading as "behind"). A day off scores `null` and never breaks a streak. */
export function computeDayScore(input: {
  slots: ScheduleSlot[];
  sessions: PomodoroSession[];
  loadIndex?: LoadIndexSnapshot;
  isDayOff?: boolean;
}): { score: number | null; sittingsClosed: number; sittingsPlanned: number; minutesLogged: number; minutesPlanned: number };
```

Surfaces:

- **Dashboard** — one line: *4 of 6 sittings closed · 185 of 260 min · score 78 · on-track streak 6d*. The streak is the existing `computeLoadIndexStreak` (`lib/loadindex.ts:122-129`), not a new one.
- **Week grid** — per-column score for past days, so Look back has something concrete.
- **Look back (Step 1)** — one more `Stat` beside the nine already there (`app/(app)/plan/week/page.tsx:566-576`): average day score. `15` already added "Days off" to that row, so the pattern is set.
- **PiP** — the score as a number, per §5.7.

What is deliberately absent, and why: **levels and badges** (they need names, and invented names are the "motivational text" plan/08 was right to ban — §8 Q4 asks the question properly); **a points currency** (a second, fictional unit competing with minutes, which are already the honest one); **loss framing** (the score is a readout, and a bad day reading low is information, not punishment); **confetti as the reward** (one brief flourish when the last sitting of a day closes is acceptable; a flourish per session is noise).

Gamification is gated behind the existing module system (`lib/features.ts`) as a `dayScore` module, so it can be turned off entirely on `/settings/features` — the same treatment `analytics`, `workload`, and `goals` get.

### 5.7 The PiP prompt, and what this does to plan/08's charter

**First, the charter.** `08.FocusOS-v2-Floating-Widget-Plan.md` §3/§12, restated in source at `lib/floating-widget.ts:1-7` and `components/floating-widget-content.tsx:13-19`, bans two things: a generic "pin anything" reminders feed, and motivational text. Both bans were right, and its two tests — **glanceable** (a number or a progress bar, not prose) and **single-tap actionable** — are the right tests.

This doc keeps the ban on a generic feed absolutely: the widget stays a fixed list, `FloatingWidgetItemId` stays an enum of named cards, and nothing becomes pinnable. It adds two cards that pass both tests:

- **`nextAction`** — renders `pickNextAction`'s existing output (`lib/next-action.ts`), which is already a deterministic cascade that already has a "starts within 15 minutes" branch (`:83-95`) and already carries the `slot` needed to pre-arm the timer (`:15-18`). One line of text, one button. This is not a reminders feed; it is the single next thing, computed the same way the dashboard's card computes it.
- **`dayScore`** — one number and a progress bar. Exactly the shape of the `loadIndex` card that already ships.

**Where this doc does narrow plan/08:** the score is motivational in intent, and saying otherwise would be dishonest. The narrowing is precise — *motivational text* stays banned (no "You've got this!", no streak-loss warnings, no praise strings); *a motivating number derived from real logged data* is permitted, on the grounds that plan/08's own stated test is "a number/progress bar, not prose," and a score is a number. Both new cards default **off** for accounts with an explicit `floatingWidgetItems` list (per `isFloatingWidgetItemEnabled`'s existing convention) and on for accounts without one, and `/settings` gets a line noting the two new items exist.

**Second, notifications — a different mechanism, stated plainly.** The PiP window is a separate `Window` with its own document; it is not a notification channel and it is Chromium-only (`components/floating-widget-button.tsx` already renders nothing where Document PiP is unsupported, per plan/08 §1.2). So:

- The in-PiP card is **not** a notification. It is a card that updates on the existing minute tick (`useCurrentMinute`, already used at `components/floating-widget-content.tsx:26`). No permission, no new API, works wherever the widget works.
- A real system notification is a separate, **opt-in, default-off** feature behind `UserSettings.sittingNotifications`. It is requested and fired from the **main** document (a provider that already runs there — `WorkdaySessionProvider` owns the day's clock and the existing reminder cadence), never from the PiP document, so it survives the PiP being closed and does not double-fire when it is open. Exactly two triggers: a sitting starting within `leadMinutes` (default 5), and a sitting's end time passing. Both dedupe per slot id per date, the same discipline `Alert.dedupeKey` (`types/index.ts:139-151`) already uses. Live `Notification.permission` is the authority; `granted` is display only. Permission is requested from a real click on `/settings` and never on page load.

### 5.8 Interaction with `14` and `15`

- **`15`'s placement is unchanged and benefits.** Its per-`capGroup` cap (`lib/weekplan.ts:201-271`) was built for exactly this shape of input: many small candidates in a named pool. Splitting tasks per §5.1 means tasks finally *have* pools (`task:<id>`), so a single big task can no longer sidestep the cap by being one indivisible block. Day-off exclusion, preferred days, and lead-time spreading all apply to sittings with no change.
- **`14`'s auto-completion is the definition of "closed."** `slotAutoStatus`'s 60% coverage rule is reused, not re-derived, so the day score can never disagree with the block strip.
- **`14`'s automatic attribution gets stronger.** `ScheduleSlot.courseId`/`bucket` stay the carriers for course work; `objectiveRef` adds the cases they never covered, so §6.2's "the timer reads the block you are in" finally includes length and paper context.
- **`scheduledMinutesThisWeek` gains a sibling, and keeps its own job.** A new `plannedMinutesThisWeek(schedules, courseId, bucket, weekDateKeys)` sums accepted *slots* carrying that course/bucket. Step 4 subtracts both it and `scheduledMinutesThisWeek` before deciding how many sittings to propose, which is the fix for §2.2's "accepting changes nothing" — and it makes `blockDecisions`' index-keyed fragility mostly moot, since the count itself now shrinks as work is accepted. §8 Q2 asks whether the index keying should be replaced outright.
- **`13`'s coherence rules hold.** Every new number has a `lib/copy.ts` entry and an `InfoHint`, and no surface shows a metric it cannot explain.

## 6. Phasing

Each phase is independently shippable and leaves the app coherent. Ordered so the data plumbing lands before anything depends on it.

**Phase 1 — Breakable work, no new UI.** `splitIntoChunks`, `remainingMinutes`, `plannedMinutesThisWeek`; the `Task`/`ScheduleSlot`/`UserSettings` fields; `acceptProposals` copying `objectiveRef`/`chunk`/`plannedMinutes`; every `taskBlockMinutes` call site switched; `taskFromTemplate` carrying `RecurringTaskTemplate.time` into the new `Task.fixedTime`. Step 4's existing list gains "n of m" labels. Verify script: `scripts/verify-chunking.ts`. **Exit:** a 14-pomodoro task appears in Step 4 as seven placeable sittings, and "Didn't fit" is empty for it.

**Callout — Phase 1 changes the shape of every existing weekly plan, with no flag.** Course-bucket candidates stop being `workMinutes`-sized and become `splitIntoChunks`-sized (§5.1), so a 3-hour revision target goes from seven 25-minute sittings to four 45-minute ones the first time the planner is opened after this ships. That is the intended improvement, and it is also the most visible consequence of the earliest phase, so it needs a line of copy on `/plan/week` the first time it happens rather than arriving unannounced. §8 Q5 covers whether 50 is the right cap.

**Phase 2 — Objectives visible.** `describeObjective`; objective chips on the week list, the day timeline block, the block inspector, and the Now card; `startFocus` taking `minutes`/`paperId`/`passNo`; callers passing the sitting's remaining minutes. **Exit:** starting a timer from a 50-minute revision block arms 50 minutes and logs a session carrying that course and bucket, with no dropdown touched.

**Phase 3 — The week grid.** The seven-column grid, drag with snap and overlap refusal, the keyboard inspector, the capacity readout updating live, the narrow-screen list fallback. **Exit:** a proposal can be moved to another day and time by pointer *and* by keyboard, and Accept writes it where it was left.

**Phase 4 — Detach and contextualize.** Step 2.5 "What's coming" with prefilled tentative times; "Accept day" removed; `syncRevisionTemplate` stops auto-creating, existing generated templates surfaced with a stop control on `/courses`. **Exit:** nothing reaches a day's schedule that the user did not confirm a time for, and every upcoming dated thing in the next 14 days appears in one list with an editable suggested time.

**Phase 5 — Score and prompt.** `computeDayScore`, the `dayScore` module, the dashboard line, the Look back stat, the two new PiP cards. **Exit:** the dashboard and the PiP agree on today's numbers, and the PiP's next-up card starts a correctly-sized, correctly-attributed session in one tap.

**Phase 6 — Notifications.** `sittingNotifications`, the permission flow on `/settings`, the two triggers with per-slot-per-date dedupe, fired from the main document. **Exit:** opting in produces exactly one notification 5 minutes before a sitting and one at its end, with the PiP open and with it closed, and none at all when opted out.

## 7. Acceptance criteria

Split deliberately. The first group is settleable by a pure-function verify script and nothing more. The second group **cannot** be settled that way and must be exercised in the running app, signed in, with real Firestore data — this project's verify scripts touch no Firestore, render no component, and drive no user flow, so reporting green scripts as evidence for anything in the second group would be reporting work as done that has not been checked.

### 7.1 Settleable by `scripts/verify-chunking.ts` (pure functions)

1. `splitIntoChunks(350, { maxChunkMinutes: 50 })` → seven sittings of 50. Sum equals 350 exactly, no element exceeds 50, none is below the 15-minute floor.
2. `splitIntoChunks(120, { maxChunkMinutes: 50 })` → `[40, 40, 40]`, not `[50, 50, 20]`.
3. `splitIntoChunks(55, { maxChunkMinutes: 50 })` → two sittings, neither below 15 — never `[50, 5]`.
4. `splitIntoChunks(30, { maxChunkMinutes: 50 })` → `[30]`. `splitIntoChunks(350, { splittable: false })` → `[350]`.
5. Every split's sum equals its input for a swept range of totals and caps — the invariant that stops minutes being created or destroyed.
6. `remainingMinutes` subtracts real session minutes: a 150-minute task with logged sessions of 22 and 40 minutes returns 88. A 6-minute session moves it by 6, not by one pomodoro. Sessions in `short_break`/`long_break` mode never count. Result clamps at 0 when overworked.
7. `plannedMinutesThisWeek` counts slots carrying a course/bucket across the week's schedules, and excludes slots on dates outside the week.
8. Fed seven sittings of one task sharing `capGroup: "task:t1"`, `placeProposals` (unchanged from `15`) spreads them across at least three working days and lands none on a day in `offDateKeys` — the regression test `15` §2.2 identified as entirely missing for `placeProposals`.
9. `describeObjective` resolves each branch in documented order and returns an `attribution` object matching `startFocus`'s parameter shape for every one.
10. `computeDayScore` returns `null` for a day with nothing planned and for a day off; returns 100 only when every sitting closed and coverage is at least 1; and ranks a day of closed sittings above a day of half-finished sittings at equal logged minutes.

### 7.2 Confirmable only in the running app

11. A real task estimated at 14 pomodoros, owned by the signed-in account, appears in `/plan/week` Step 4 as seven labeled sittings on at least three different days, and **not** under "Didn't fit".
12. A `RecurringTaskTemplate` with `time: { startTime: "14:00", endTime: "15:00" }` generates a task that the planner places at 14:00–15:00 as one block — not as a 25-minute block at an unrelated time (the defect this repo has already produced in live use).
13. Dragging a proposal in the week grid to another day and time moves it, refuses to overlap a lecture, snaps to 15 minutes, and Accept writes it at the dropped time — verified by re-opening `/plan/day` for that date and seeing the block there.
14. The same move is completable with keyboard only: Tab to the proposal, Enter to open the inspector, change day and time, Accept.
15. Starting a focus session from a 50-minute revision block arms **50:00**, not 25:00, and the resulting `PomodoroSession` carries that block's `slotId`, `courseId`, and `bucket`.
16. Resuming a sitting already 22 minutes covered arms 28 minutes, and the "carried over" figure shown on the next sitting of the same `chunk.groupId` matches.
17. Accepting a bucket's proposals and re-deriving Step 4 does **not** re-offer the same minutes — `plannedMinutesThisWeek` has absorbed them.
18. Starting a reading block from the timeline produces a session carrying `paperId` (and `passNo` where the block specifies one), and the paper's own progress reflects it.
19. After Phase 4, no block appears on any day's schedule that the user did not confirm a time for: "Accept day" is gone, and creating a course with a revision target produces no recurring task instances.
20. "What's coming" lists every dated thing in the next 14 days with a prefilled time, and editing a prefilled time then accepting places the sitting at the edited time.
21. The PiP window shows the next-up card with the correct sitting, its objective, and its start time; **Start** arms the right length and attribution; the card updates on the minute tick without the PiP being reopened.
22. The dashboard's score line and the PiP's score card show the same numbers for the same day, and both match what the day's blocks and sessions actually contain.
23. With `sittingNotifications` on, exactly one notification arrives 5 minutes before a sitting and one at its end — with the PiP open and with it closed, never twice — and none arrive with the setting off or the permission denied.
24. Turning the `dayScore` module off on `/settings/features` removes every score surface with no broken layout and no orphaned copy.
25. `npm run typecheck`, `npm run lint`, `npm run build`, and every existing `verify:*` script stay green. Necessary, not sufficient — see the note opening §7.

## 8. Open questions — real product decisions, flagged rather than assumed

**Q1 — Does "detach course things from timeline" include lectures?** §1 A1 assumes not: a `CourseSession` is externally fixed, and a timeline without lectures would misrepresent the day. The stronger reading — lectures move to a separate "fixed commitments" lane, leaving the timeline purely for chosen work — is coherent and would change §5.4 substantially. Needs a yes/no before Phase 4.

**Q2 — Should `blockDecisions`' index keying be replaced?** `key = \`${index}\`` (`lib/weekplan.ts:244`) means every stored accept/dismiss silently re-targets when the candidate list changes (§2.2). §5.8 makes it mostly moot by shrinking the count as work is accepted, but "mostly" is not "fixed." A content-derived stable key (a hash of objective + duration + index within its group) is a small change with a migration question attached: existing `blockDecisions` maps would no longer resolve. Worth doing, worth deciding when.

**Q3 — Is a sitting a slot forever?** §5.1 argues against a `workChunks` collection for this user at this scale, and names the cost: progress is a client-side derivation over the week's schedules plus the week's sessions rather than one indexed query. If sittings ever need to be queried across weeks — "show me every sitting at this task, ever" — that inverts.

**Q4 — Levels and badges: wanted, or noise?** §5.6 deliberately ships a score, a streak, and a sittings count, and no named tiers, because names are the "motivational text" plan/08 banned. "Gamify it" may well have meant the named-tier version. If so it is a small addition on top of `computeDayScore` — but it should be an explicit yes, not an assumption, because it is the part most likely to feel patronizing in six months.

**Q5 — What is the right maximum sitting?** `DEFAULT_MAX_CHUNK_MINUTES` is proposed at 50 — two classic pomodoros, a plausible deep-work block, and a length that fits between typical routine blocks. It is also the number that changes a 3-hour revision target from seven 25-minute sittings to four 45-minute ones (§5.1), which is a real change in how the week reads. 50 is a starting point, per-task overridable and globally settable; it should be revisited after a week of real use.

**Q6 — Should the day score be visible while the day is in progress?** A live score is motivating at 16:00 and demoralizing at 09:00, when it is structurally near zero. Options: show it only after a threshold of the day has elapsed, show it as "on pace" rather than absolute, or show it always and accept the morning zero. Not decided here.

**Q7 — What happens to a sitting whose work is finished early?** If a task's `remainingMinutes` hits 0 while three sittings of it are still on future days, those blocks are stale. Silently deleting them touches the user's schedule without being asked; leaving them lies. A banner on `/plan/day` offering to clear them is the likely answer, and it is the kind of small seam that only shows up in real use.

**Q8 — Should the auto revision template be removed, or made opt-in?** §5.4 removes it, and names the cost: weekly planning becomes mandatory for revision to happen at all. The alternative is keeping `syncRevisionTemplate` behind a per-course "generate revision tasks automatically" switch, default off for new courses and on for courses that already have one — additive, no regression for the passive path, but it keeps alive the exact mechanism that puts course work on days nobody chose. This is the one decision in the doc that could reasonably go the other way, and it should be settled before Phase 4 rather than during it.
