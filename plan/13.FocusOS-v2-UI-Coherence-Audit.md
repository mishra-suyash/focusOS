# FocusOS UI Coherence Audit — "Things in the UI Don't Make Sense"

## Scope and method

This is a **coherence** audit, not a layout audit — `plan/09.FocusOS-v2-UI-UX-Audit.md` already covers mobile-nav/spacing/loading-flash issues (all marked implemented there) and is deliberately not repeated here. The question this doc answers instead: for every label, number, button, and flow a user sees, does it say what the underlying code actually does, and is it consistent with every other label/number/button making the same claim elsewhere in the app?

**Every route in the app was covered** (`app/**/page.tsx`, 27 pages) plus the shared shell (`app-shell.tsx`, nav, floating widget) and every component/lib file each page pulls in one level deep, split into four areas surveyed in parallel:

- **Area A — Daily flow**: Dashboard, Tasks, Plan/Day, Plan/Calendar
- **Area B — Study surfaces**: Courses, Goals, Papers (list + detail), paper reading window, Revise (`/review`)
- **Area C — Reflection & config**: Daily/Weekly reviews, Analytics, AI Insights, Settings (+features, +routine), Help
- **Area D — Admin & entry**: Login, all `/admin/*` pages, the app shell/auth provider shared by everything

**Method**: static reading of page/component source (literal JSX copy and labels, not just prop names) cross-referenced against the `lib/*.ts` business logic each number/label is actually sourced from. A live authenticated browser pass was **not** available this session (no active session on the local dev server, and signing in is outside what this assistant does on a user's behalf) — every finding below is sourced from and cites exact code, not a screenshot. Treat layout-only symptoms (would this look fine once rendered?) as unverified; treat logic/copy mismatches (does this label match what the code does?) as directly confirmed from source.

**81 findings** across the four areas, plus 8 cross-cutting themes below that tie findings from different areas to the same root cause.

## Cross-cutting themes

These recurred independently across two or more of the four (independently-run) survey areas — that convergence is itself a signal they're real, systemic issues rather than one-off nitpicks.

### T1. The "Load Index → Workload" rename was never finished
Refs: **A11, C3**. `components/vocabulary-rename-dialog.tsx` and `/help` both tell users "Load Index (LI)" was renamed to "Workload" everywhere. The dashboard widget (`load-index-widget.tsx`) and every page-level label honor it. But the floating/PiP widget (`lib/floating-widget.ts:14`, `components/floating-widget-content.tsx:85`) still says "Load Index" — and per A11, it also reads a stale cron-computed snapshot rather than the same live value the dashboard shows, so it's both the old name **and** potentially a different number for what's supposed to be one concept.

### T2. The Workload/Load Index numbers disagree with themselves and with other pages
Refs: **A1, A25, A30, B8**. The dashboard widget's own headline ratio and its caption text use different denominators (A1: one is floored at 30 minutes, the other isn't) and can contradict each other outright (100% in the caption, "Behind" in red on the badge). The Morning Brief card shows a frozen ~6am snapshot of the same "required minutes" number the widget recomputes live all day, with nothing marking one as stale (A25). The color scale collapses two opposite problems ("behind" = too little done, "overrun" = too much) into the identical red (A30). And the Courses page reuses the same color badges with the text legend dropped, so the same color means something different depending which page you're on (B8).

### T3. "Insights" (Settings toggle) vs "AI Insights" (everywhere else)
Refs: **C4, D8**. `lib/features.ts`'s module label is bare "Insights"; the page itself, the nav, and the Help page all call it "AI Insights." A user scanning Settings → Features for "AI Insights" won't find that string.

### T4. Help's "what's optional" sentence is stale
Refs: **C5, D9**. `app/(app)/help/page.tsx`'s one-sentence list of optional modules ("Courses, Revise, Goals, Weekly check-in, Workload, and Analytics are optional") omits three real toggleable modules the code actually has: Paper tools, AI Insights, and Plan's day-timeline variant. A user relying on this sentence to know what can be turned on/off gets an incomplete picture, and (per D9) specifically won't learn why AI Insights vanished from their nav if they disabled it.

### T5. "Revise"/"review" names three unrelated features
Refs: **B2, B7, C15**. (1) A course's "Revision hours/week" field auto-creates a plain recurring *Task* titled "Revise \<course\>". (2) The nav's "Revise" item (route `/review`, singular) is a completely different spaced-repetition flashcard queue sourced from class logs and paper verdicts. (3) `/reviews/daily` and `/reviews/weekly` (plural) are yet another unrelated pair of reflection pages ("Daily wrap-up," "Weekly check-in"). Nav *labels* stay distinct enough for a careful user, but a user who sets "Revision hours/week" expecting it to feed the flashcard queue is wrong, and anyone reading routes/code (including future maintainers) hits a real naming trap.

### T6. The course's four weekly buckets: three of four rows are decorative
Refs: **B3, B4, A12, A13**. The "This week's buckets" panel added most recently shows Goal/Assignment/Backlog/Revision as four visually identical rows (label + editable hours + Save). Only Revision has any downstream effect — it auto-creates a task and feeds the daily Workload computation. Assignment and Backlog are pure `updateCourse` bookkeeping: stored, redisplayed, and read by nothing else in the app (B3). The one `InfoHint` attached to the whole panel describes only Revision's behavior, misleadingly implying all four rows work that way (B4). Symmetrically, the Tasks page's own bucket picker (which is what actually assigns a task to one of these four buckets) has zero visible label or explanation of what a bucket does or which of the four are "real" (A12), and silently drops the chosen bucket with no warning if the course is cleared before submitting (A13).

### T7. "Slot" survived the "Block" rename in the same widget that otherwise uses "block"
Ref: **A14**. `lib/copy.ts` documents `Slot → Block` as a completed rename, and `daily-schedule-widget.tsx` uses "block" correctly in two places — but says "slots" in three others in the same card. A narrower instance of the same "incomplete rename" failure mode as T1.

### T8. A "Google Calendar" slot-type option exists with no Google Calendar integration wired to it
Ref: **A5**. `slotTypeLabels.external = "Google Calendar"` is selectable in every block-type dropdown today; nothing in the codebase ever programmatically creates one, and picking it silently locks the block with no explanation. (The real Google Calendar sync feature, `plan/11...`, is a separate, unrelated-to-this-dropdown effort.)

## Area A — Daily flow (Dashboard, Tasks, Plan/Day, Plan/Calendar)

### Critical

**A1. The Workload widget's two numbers can contradict each other.**
`lib/loadindex.ts:85-93` computes `value = actualMinutes / Math.max(requiredMinutes, 30)` (denominator floored at 30) but returns the *unfloored* `requiredMinutes` for display. `components/load-index-widget.tsx:29-32` prints both: on a near-empty day (`required=5, actual=5`), the caption reads "5m done of 5m required today" (100%) while the headline ratio is `0.17` and the badge says **Behind** in red — same widget, same instant, disagreeing about whether the day is done.
*Fix:* use the same floored denominator for both the ratio and the displayed "required" text, or show the true unfloored value in both places.

**A2. "On-track streak" doesn't measure being on-track.**
`app/(app)/dashboard/page.tsx:216` labels a tile "On-track streak" using `metrics.streak` (`lib/analytics.ts:16-24` — consecutive days with ≥1 completed focus session, regardless of workload). The Load Index widget on the *same page* shows a differently-computed "N-day streak" (`computeLoadIndexStreak`, `lib/loadindex.ts:109-117` — consecutive days at Load Index ≥ 0.9) with a hint literally reading "Days in a row you hit your planned workload." `lib/loadindex.ts:109`'s own comment says the LI-streak "replaces the old pomodoro streak" — but the metrics tile still shows the old one under a name that only accurately describes the new one. A user can do one 5-minute pomodoro and see "On-track streak: 12d."
*Fix:* rename the metrics tile (e.g. "Active-day streak") or point it at `computeLoadIndexStreak` too.

**A3. "Clear all" is enabled and silently does nothing on a brand-new account's first day.**
`components/plan/day-timeline-editor.tsx:436-444`: `disabled={!slots.some(slot => slot.type !== "class")}`. Default routine blocks (Sleep, Breakfast, Lunch, Dinner — `locked: true` but typed `sleep`/`meal`, never `"class"`) satisfy that condition, so the button stays enabled with only routine blocks present. But `clearUnlockedSlots` filters by `isLockedSlot` (class ∥ external ∥ `locked:true`) — routine blocks pass that filter too — so nothing is actually cleared and the function returns before any confirm dialog or toast. Click "Clear all" on day one and nothing visibly happens, with no explanation why.
*Fix:* base the `disabled` check on the same `isLockedSlot` predicate `clearUnlockedSlots` itself uses.

**A4. A locked class/routine block can be silently unlocked via its own type dropdown.**
`components/plan/block-inspector.tsx:65-90` shows a "Class block — locked here" banner and correctly disables the time inputs, but the type `<select>` two lines below has no `disabled` at all. Changing a locked block's type away from `"class"` makes `isLockedSlot` (`lib/schedule.ts:100-102`) return `false` on the next render — the block becomes draggable/deletable immediately, contradicting the still-visible "locked" banner. The identical unguarded select exists in the classic editor's `SlotEditor` (`app/(app)/plan/day/page.tsx:342-344`).
*Fix:* disable the type select too whenever `isLocked`.

**A5. A "Google Calendar" slot type exists with no Google Calendar integration behind it.**
See **T8** above.

**A6. "Finish" on the focus timer logs the full planned duration, not time actually worked.**
`components/focus-session-provider.tsx:251` wires "Finish" (next to "Reset," `SkipForward` icon) straight to `completeSession()` with no elapsed-time argument; `completeSession` builds `{ minutes: duration, ... }` — the *configured* session length, not elapsed time. Clicking Finish 30 seconds into a 25-minute session still logs 25 completed minutes, flowing into `focusedMinutes`, into Workload's actual-minutes, and — if linked — into a task's `completedPomodoros` at full credit. Nothing in the UI signals this awards full credit regardless of when you click it.
*Fix:* compute actual elapsed time for "Finish," or relabel it to make clear it counts the full session.

**A7. Focus sessions started from a scheduled block never credit the linked task.**
`focus-session-provider.tsx:216-226`'s `startFocus()` (used by the Dashboard's "Start focus session from a block" flow) explicitly does `setTaskId("")`. `finalizeSession` only increments `completedPomodoros` when `data.taskId` is set. A task worked entirely via its scheduled block never gets credited — `task-list.tsx`'s "0 of 3 focus sessions · 3 left" stays frozen at 0 no matter how many real sessions the user runs against that block.
*Fix:* thread the block's `assignedTaskIds` through to `startFocus`/`taskId` when a block has exactly one linked task.

**A8. Classes vanish from Plan Day and Calendar with zero explanation if the user has no Term set up.**
`lib/terms.ts:9-11`, `isBreakMode` returns `true` whenever there's no active term at all. Both `plan/day` and `plan/calendar` gate `courseSlotsForDate` behind `!isBreakMode(...)`. A user who adds Courses (a module that doesn't itself require Terms) but never creates a Term sees an empty calendar and no class blocks on any day, forever — no banner, no empty-state hint, no link explaining a Term is needed first.
*Fix:* add an empty-state hint on Plan/Calendar when courses exist but no active term does.

**A9. `scheduleSummary`'s "completed" counts elapsed clock time, not actual work.**
`lib/schedule.ts:164-171`: `completedDeepWork`/`completedSlots` both trigger purely on `minutesFromTime(slot.endTime) <= minute` — the block's scheduled end time has simply passed. The daily schedule widget displays these as "Deep work done" and "N of M planned slots completed." A user who did zero work all day but whose blocks have all timed out sees "100% day complete," the opposite of what happened, with no visual distinction from a block genuinely marked `status: "completed"`.
*Fix:* distinguish "time has passed" from "marked complete" in both the computation and the copy.

**A10. `pickNextAction`'s displayed reason is false for its own fallback branch.**
`lib/next-action.ts:71-79`: the task branch's `why` is hardcoded `"Highest-priority open task due this week"` for *both* the actually-priority-sorted match and the `?? openTasks.find(...)` fallback, which is a plain first-match with no priority sort at all. `next-action-card.tsx` displays this verbatim, so a user can be told a task is "highest-priority" when priority was never consulted.
*Fix:* give the fallback branch its own, honest `why` string.

### Medium

**A11. "Load Index" survives in the floating/PiP widget after the app-wide rename to "Workload."** See **T1**.

**A12. The task bucket picker has zero user-facing explanation.** See **T6**.

**A13. The bucket choice is silently dropped if the course is cleared before submit.** See **T6**.

**A14. "Slot" leaks past the app's own rename to "Block" inside one widget that otherwise says "block."** See **T7**.

**A15. The same widget names itself three different things.**
`components/daily-schedule-widget.tsx`: empty-state heading "Daily schedule," populated small label "Full-day schedule," populated large heading "Today in progress" — three names for one widget depending on whether it has data.
*Fix:* pick one name and keep it across states.

**A16. "Day wrap-up" vs "Daily wrap-up" — one feature, two names one click apart.**
`app/(app)/reviews/daily/page.tsx` uses "Daily wrap-up" (the canonical name in `lib/copy.ts`); the compact sheet opened by "End day," `components/day-wrapup-sheet.tsx`, calls itself "Day wrap-up" and has a button reading "Open full wrap-up" that navigates to the page named differently than itself.
*Fix:* use "Daily wrap-up" consistently in the sheet too.

**A17. The better Plan/Day editor (the new timeline) has no discoverable entry point.**
`lib/features.ts`: `planDayTimeline` is opt-in, excluded even from the "everything" pack. The only way to reach it is `/settings/features`, which the Plan/Day page never links to or mentions. Drag-and-drop, autosave, undo/redo, the task tray, AI templates, and "Shift rest of day" are all invisible to anyone who hasn't independently found that settings page.
*Fix:* surface a "Try the new day view" callout on the classic Plan/Day page.

**A18. Turning the new timeline editor on removes template browsing/apply, leaving only a one-way path.**
With `planDayTimeline` on, the entire template aside (Browse/Apply/Save as template/Set as workday template) is hidden, and "Browse templates" was the only thing that ever opened `TemplateGalleryDialog` — so that dialog becomes unreachable. The timeline editor only exposes "Save as template," not apply; "Update existing template from this day" still lets you push the day *into* a template, but nothing pulls a template *onto* the day anymore. A real capability loss most users would never notice they lost.
*Fix:* add an "Apply template" action to the timeline editor's own tray.

**A19. "Update template blocks" gives no feedback on success or failure.**
`app/(app)/plan/day/page.tsx:288-297`: reads a select via `document.getElementById`, silently no-ops on validation errors, and on success calls `updateDayTemplate` with no toast. The one error banner that would explain a refusal is itself gated off in timeline mode, so a blocked update fails completely silently there.
*Fix:* add a toast/inline confirmation for both outcomes, independent of editor mode.

**A20. "Tasks to schedule" in the Plan/Day tray never shows the block size it will create; the adjacent Quick Blocks do.**
Task rows show only title + "Schedule"; Quick Block chips explicitly print `"{label} · {minutes}m"`. Since `taskBlockMinutes` can size a task block anywhere from 25 minutes to hours, a user has no idea how much of the day a task will consume until after it's placed (the drag-ghost preview also omits minutes).
*Fix:* print the computed duration next to each task row, same as Quick Blocks.

**A21. Calendar day cells silently truncate at 2 items with no overflow indicator.**
`app/(app)/plan/calendar/page.tsx`: `classes.slice(0, 2)` and `dueTasks.slice(0, 2)` — a day with 5 due tasks looks identical to one with exactly 2.
*Fix:* add a "+N more" affordance.

**A22. The Calendar's "planned" dot can appear for a day with zero actual blocks, and has no visible label.**
`hasSchedule = schedules.some(s => s.dateKey === dateKey)` checks only that a `DailySchedule` doc exists, not that it has any slots — a deliberately emptied day (e.g. after "Clear all") still shows the green dot. The dot also has no `title`, only `aria-label`, so a sighted mouse user can't learn what it means without a screen reader.
*Fix:* check `slots.length > 0`; add a hover title.

**A23. Category dropdowns show raw lowercase values where the task list shows proper-cased labels.**
`task-form.tsx` and `evening-rollup-card.tsx` both render literal `"research"`/`"coding"` option text; `task-list.tsx` shows the same categories via `categoryLabels[...]` → "Research"/"Coding." Same concept, same page family, different casing depending on create vs. view.
*Fix:* use `categoryLabels` in the option text too.

**A24. The Dashboard Customize dialog doesn't say it only controls a fraction of the page.**
`dashboard-customize.tsx` titles itself plain "Customize" over a 5-item checkbox list; unchecking all 5 still leaves Focus timer, Today's tasks, Daily schedule, and Reading now permanently on-screen (core cards are never gated, per the code's own comment) — nothing in the dialog says so.
*Fix:* a one-line note in the dialog ("Focus timer, tasks, schedule, and reading are always shown").

**A25. The Morning Brief's "target minutes" can silently drift from the live Workload number it duplicates.** See **T2**.

**A26. Tasks page flashes the wrong empty state on every load for existing users.**
`app/(app)/tasks/page.tsx` destructures only `{ items: tasks }`, discarding the `loading` flag `useUserCollection` provides. `tasks.length === 0` drives the empty state, so any user with real tasks sees "Add a task" flash before the Firestore snapshot arrives — `plan/day/page.tsx` uses the same hook's `loading` flag correctly elsewhere in this codebase, so this is an inconsistency in care, not a missing capability.
*Fix:* gate the empty state on `!loading && tasks.length === 0`.

**A27. "Inbox" on the Tasks page means "everything," not an inbox.**
`view === "inbox" ||` is unconditionally true in the filter clause, so selecting "Inbox" (the default view) is identical to no filter at all, including already-done tasks — despite a separate "Completed" view and "All statuses" filter existing. The label conventionally implies a specific unsorted subset; here it means "all."
*Fix:* either make Inbox actually filter to unprocessed/no-due-date tasks, or rename it "All."

**A28. Dashboard's "Today's tasks" drops metadata the Tasks page shows for the identical task.**
Dashboard renders each task with only a checkbox, title, and pin star — no priority, category, course chip, due date, or the "Hard deadline" badge `task-list.tsx` shows for the same `Task` object on `/tasks`. A pinned hard-deadline task (visa renewal, submission portal — exempt from Workload) shows on Dashboard with no flag that it's exempt, and no due date, even though pinned tasks aren't restricted to being due today.
*Fix:* reuse (or a compact variant of) the same task-row component on both pages.

**A29. "In progress" has no pressed/active state and no way back to "todo."**
`task-list.tsx`: a plain text-styled button, always visible regardless of the task's current status, with no visual indication of which state is current — the checkbox is the list's only status distinction. Combined with A27, a user can filter by "in_progress" but the list itself never visually shows which tasks are in that state.
*Fix:* style the button to reflect current status; add a way to revert to "todo."

### Low

**A30. Load Index band colors collapse two opposite problems into the same red.** See **T2**.

**A31. No visible legend for the plan timeline/calendar's type colors.**
`day-strip.tsx` and `plan/calendar/page.tsx` rely entirely on native `title` hover tooltips or bare color chips to communicate block/event type — no visible legend, so touch users get nothing and desktop users must hover each block individually.
*Fix:* a small static color-key, even just in an `InfoHint`.

**A32. Focus session label defaults to "writing" for every new session until "More options" is opened.**
Unless a task is linked (which overwrites it) or the collapsed label/category section is expanded, every logged session's `label` is the literal string "writing" — "Today history" can show a user's reading/coding/admin sessions all mislabeled "writing."
*Fix:* default the label from the currently selected category instead of a fixed string.

**A33. "Cycle N" has no explanation of what it means, and shows identically during breaks.**
`pomodoro-timer.tsx`: `Cycle {cycle} · {duration} minutes`, no `InfoHint`, unchanged copy whether in a work or break period.
*Fix:* add a short `InfoHint`, or suppress/relabel during breaks.

## Area B — Study surfaces (Courses, Goals, Papers, paper reading window, Revise)

### Critical

**B1. A paper's "Progress" bar and its reading-time display are two uncorrelated metrics with no explanation, and progress never reflects the reading window.**
`lib/papers.ts`'s `derivePaperProgress` is hardcoded 0/33/66/100, keyed only to `pass1/pass2/pass3.status`. The full-screen reading window logs free-reading time via `savePomodoro` with `paperId` set, but never touches `paper.progress`/`paper.status`. A user can spend hours highlighting/annotating a PDF (reading-time counter climbing right next to the bar) while the progress bar stays frozen at 0% and status stays "To read" forever, because progress is derived exclusively from the old Pass 1/2/3 system and is blind to the newer reading-window feature entirely.
*Fix:* either fold reading-window engagement into `derivePaperStatus`/`derivePaperProgress` (e.g. "reading" once any session exists), or visually separate "progress through passes" from "time spent" so they don't read as the same signal.

**B2. "Revision hours/week" on a course creates a recurring Task, colliding in name with the unrelated spaced-repetition "Revise" queue.** See **T5**.

**B3. Only one of the course card's four weekly-bucket rows has any effect beyond bookkeeping.** See **T6**.

**B4. The one InfoHint on the buckets panel describes only the Revision row, misleadingly implying all four work that way.** See **T6**.

**B5. A Goal's `targetHoursPerWeek` displays in full on every course it's linked to, not divided.**
`lib/courses.ts`'s `bucketWeeklyTarget` sums linked goals' hours with no division by number of linked courses. Meanwhile `lib/goals.ts`'s `goalTargetMinutesForDay` correctly sums each goal's hours only once, globally, for Workload — so Workload itself isn't double-counted, but the *per-course display* is misleading about what the number represents. A user with one 10h/week goal linked to 3 courses sees "10h/week (from linked goals)" on each of the three cards, easily read as 3× the actual commitment.
*Fix:* split the goal's hours across its linked courses for display, or label it "shared with N other course(s)."

### Medium

**B6. Two UI surfaces both claim to plan a course's weekly hours (the course card's buckets vs. the Goals module), linked only by a small inline note.**
To change the Goal-bucket number seen on a course card, a user must navigate to Goals, find the right goal, and edit its `targetHoursPerWeek` there — nothing on Courses links there directly.
*Fix:* make the "(from linked goals)" text a link to the relevant goal(s).

**B7. `/review` (singular, "Revise") vs `/reviews/daily`+`/reviews/weekly` (plural) — unrelated features sharing near-identical route stems.** See **T5**.

**B8. The Courses page's weekly-buckets badge reuses the Workload color scale but drops the text label.** See **T2**.

**B9. "Generate now" inside one course's Recurring Commitments section actually regenerates tasks for every course's recurring commitments, discoverable only via a hover tooltip.**
The button lives inside a single course's `<article>`, right next to that course's own recurring-commitment list, strongly implying per-course scope; its real (global) scope is explained only in a `title` attribute most users won't hover to read.
*Fix:* move the button to a page-level location, or add a visible caption.

**B10. Pausing a course's auto-revision task leaves the Revision bucket's target number unflagged — it looks like it's still being pursued.**
The code's own comment notes raising the hours again never force-reactivates a template paused by hand — but the Revision `BucketRow` has no awareness of the template's paused state at all.
*Fix:* show "(auto-task paused)" on the Revision row when the linked template is inactive.

**B11. Checkpoint's "Wt %" (weight percentage) is captured on creation but never displayed anywhere afterward.**
`checkpoint-form.tsx` collects it; `CheckpointRow` on the Courses page renders type badge, title, star, due date, status, result score/max — never `weightPct`. Write-only from the UI's perspective, no confirmation it saved, no later use.
*Fix:* show `weightPct` on the checkpoint row; consider using it for a weighted-grade summary.

**B12. The Revise queue's "N due now" is the count *after* daily caps are applied, not the total actually due, with no indication anything was trimmed.**
If 50 items are due but the daily cap is 20, the header reads "20 due now" — read naturally as a total-due count, not a post-cap display count.
*Fix:* show "20 of 50 due now (daily cap reached)" whenever the raw due count exceeds the capped queue.

**B13. "Read" is used for three different things on one page: the terminal paper status, the Pass 2 section heading, and the reading-window feature.**
Status card shows "Status: Read"; the Pass 2 section heading is "Read — grasp the content" right below it; "Open reading window" is a third, separate button. Not a functional bug, but a new user glancing at "Status: Read" next to a section titled "Read —..." may wonder whether the paper is done or mid-pass.
*Fix:* rename the Pass 2 heading to drop the leading "Read —".

**B14. The auto-revision recurring-commitment row's "Clear hours to stop" is plain non-interactive text, not a link back to where the hours field lives.**
The instruction is correct but nothing here is clickable or scrolls the user to the actual input.
*Fix:* make it a real button using the same `focusSection` scroll-to pattern already used elsewhere on this page.

### Low

**B15. "Reading time" and pass-based "Progress" use unrelated timeframes with no legend clarifying they're independent.** (Narrower restatement of B1 for the list page specifically — no `InfoHint` on either number.)
*Fix:* add a short `InfoHint` to "reading time."

**B16. The Revise queue's empty state omits two of the four real ways a card gets created** (Pass 3's structure-recall grade, and starting revision on a paper set) — only mentions logging a class or saving a paper for later.
*Fix:* extend the empty-state copy or link to a short "how cards get here" explainer.

**B17. "Promote to task" on a paper note has only an `aria-label`, no visible `title` tooltip, unlike most icon-only buttons elsewhere in the codebase.**
*Fix:* add `title="Promote to task"` for parity.

**B18. Paper detail's Skim/Read/Deep dive section subtitles get inconsistent `InfoHint` treatment — only Skim has one, despite Deep dive's own non-obvious "(opt-in)" qualifier.**
*Fix:* add InfoHints consistently to all three, or drop the one on Skim.

## Area C — Reflection & config (Reviews, Analytics, Insights, Settings, Help)

### Critical

**C1. "Turn on Workload" (a nudge banner button, and the equivalent Settings → Features toggle) silently does nothing visible.**
Both only flip the **feature module** `workload` in `lib/features.ts`. Nothing in the app gates any UI on `isEnabled("workload")` except this nudge and the alert-type map — the actual Workload *card* on the dashboard is a completely separate toggle (`DashboardWidgetId "workload"`, `lib/dashboard-widgets.ts`), defaulting off for every pack except "everything," only changeable via the dashboard's own "Customize" dialog (unreachable from Settings). A user who clicks "Turn on" — or enables Workload under Settings → Features — sees no change anywhere.
*Fix:* either make the module toggle actually control `dashboardWidgets`, or remove the module-level toggle and route users straight to the dashboard's Customize control.

**C2. AI Insights' empty state states a false precondition.**
"No insight yet for today. Click 'Regenerate' or wait for the scheduled morning run (**requires an AI provider key configured**)." But `insight.daily` defines a deterministic fallback, and both the API route and the cron job always produce output (provider: "fallback", degraded: true) when no key is configured — regenerating or waiting **always succeeds**, producing a rule-based insight. The copy tells users a working feature is blocked on setup they can't perform, likely causing them to never click the button.
*Fix:* drop the parenthetical, or reword to state that unconfigured accounts still get a rule-based summary.

### Medium

**C3. "Load Index" leaks in the Floating Widget after the app-wide rename to "Workload."** See **T1**.

**C4. "Insights" (module label) vs "AI Insights" (everywhere else).** See **T3**.

**C5. Help's "optional features" list omits three real toggleable modules.** See **T4**.

**C6. Weekly check-in's metrics strip silently mixes different time windows.**
Of 5 tiles, two are explicitly labeled with their window ("this week", "14-day"); "Today focus minutes" injects a single day's number into an otherwise weekly strip with no distinguishing treatment; "Skim drop/park rate" is actually an **all-time** ratio (no date filtering at all) shown with no window qualifier next to two tiles that do state theirs.
*Fix:* label every tile with its window ("today," "this week," "all-time").

**C7. Inconsistent `InfoHint` coverage across equally-opaque metrics on the same strip.**
"On-track streak" and "Catch-up hours (14-day)" get an `InfoHint`; "Skim drop/park rate" — which requires knowing "Skim" = Pass 1 and that two different triage verdicts are merged into one percentage — gets none.
*Fix:* add the missing hint, or make hint coverage consistent app-wide.

**C8. Disabling a routine block doesn't visually disable its day-of-week picker.**
Unchecking a block's "Enabled" checkbox leaves the Sun–Sat day-toggle buttons directly below it rendered exactly as active as an enabled block's — no dimming, no disabled state. A user could pick days for a block that's actually off with zero feedback those clicks currently do nothing.
*Fix:* gray out / disable the day picker and time fields when `block.enabled` is false.

**C9. `workMinutes` silently drives numbers across Courses/Plan/Revise, but is never exposed as a labeled Settings control.**
It's only ever set by applying a focus-timer preset, yet it resizes revision-block time estimates, course weekly-hours totals (rendered on Courses), and Plan block durations. Nothing on Settings — which otherwise explains `maxRevisionsPerDay`/`maxRevisionMinutesPerDay` well — mentions that changing your Pomodoro length elsewhere changes these numbers too.
*Fix:* add a labeled "Work session length" field to Settings with a note on its downstream effects, or cross-reference it near the Revision/Plan sections.

**C10. AI health panel exposes raw internal jargon.**
"Claude: circuit open," "Ollama: unreachable" — "circuit open" is a resilience-pattern term with no in-UI explanation; a non-engineer can't tell this means "temporarily disabled after repeated failures, retrying automatically" vs. something they need to fix.
*Fix:* map internal states to plain language, or add an `InfoHint`.

**C11. "Plan — Day timeline" is listed as a peer of Courses/Goals in the Features toggle list, though it's a UI variant of an existing page, not a new destination.**
Nothing distinguishes "this adds a page" from "this changes how an existing page looks" in that flat list.
*Fix:* visually separate UI-variant toggles from feature-area toggles.

## Area D — Admin & entry (Login, `/admin/*`, app shell)

### Critical

**D1. "Signup mode" admin control is fully decorative — it changes nothing.**
`admin/settings` renders a "Signup mode" select (Open / Invite only / Closed) that calls `save({ signupMode: ... })`. `signupMode` is only ever read where it's defined and defaulted — no API route, sign-in flow, or auth logic ever checks it. `/login` and the public sign-in-methods route only look at the separate `signInMethods` checkbox list and `maintenanceMode`. An admin who sets this to "Closed" believes new signups are blocked; anyone can still sign up via any enabled method.
*Fix:* wire `signupMode` into the sign-in-methods/auth guard, or remove the control until implemented.

**D2. "Max active users" doesn't cap active users — it's a hidden multiplier in a spend-estimate formula.**
The only consumer computes `effectiveCapUsd(defaultUserBudgetUsd * maxActiveUsers)`, used purely for the "Month-to-date AI spend" cap on Overview. It does not gate signups, disable accounts, or throttle anything — the real cron-processing safety cap is a separate hardcoded constant unrelated to this field. The label reads as a hard ceiling on user count; it's an input to a budget display.
*Fix:* rename to "Users assumed for budget estimate," or actually enforce it as a cap.

**D3. The Users table's "Budget/Quota" column shows the raw per-user override, not the effective (tier-inherited) value — reads as "$0 budget" for almost every user.**
Per the type's own doc comment, these fields are "per-user override on top of the assigned tier's limits" — most users have neither set. The code elsewhere already computes the correct *effective* value (`userData?.monthlyBudgetUsd ?? tierLimits.aiMonthlyBudgetUsd`), but the Users page never calls it — it just prints the raw override, so a normal tier-assigned user shows "$- / - MB," reading as zero budget/quota rather than whatever their tier actually grants.
*Fix:* display the resolved effective value, with an indicator for override vs. inherited.

**D4. "Sign out" (force-revoke) gives zero success feedback.**
Every other mutating action on the Users page (`patch`, `assignTier`, `sendInvite`, `runDelete`) reloads the table after success to confirm it worked. `revoke()` does neither — no reload, no toast, no state change beyond clearing the busy flag. Clicking "Sign out" looks like it did nothing even though it silently succeeded server-side.
*Fix:* show a transient confirmation, matching the other actions' pattern.

**D5. The Ollama admin page hides the currently-configured model unless you re-test the connection.**
The "Model" select (and thus any visibility of the saved `config.model`) only renders when a connection test just succeeded. On page load, the actually-saved model is never shown anywhere else — if Ollama is temporarily unreachable, the configured model is completely invisible even though it's already saved.
*Fix:* show the saved model as plain text unconditionally, independent of the test result.

### Medium

**D6. "Role" and "Status" selects both offer "disabled," implying two independent mechanisms when there's really one.**
Server-side, the two are forced into lockstep — setting either flips the other — but nothing in the UI communicates that; two adjacent selects sharing a value looks like two settings an admin must remember to keep in sync.
*Fix:* merge into one control, or add a note clarifying they're mirrored.

**D7. Admin number inputs auto-save on every keystroke while adjacent text inputs require an explicit Save click, with no visual distinction.**
"Max concurrent calls" and "Max active users" fire a write after every digit typed; the Ollama page's own `baseUrl` field a few lines above requires clicking "Save address." Same page, two save models, no indicator distinguishing them.
*Fix:* make save behavior consistent per field type, or add a per-field save affordance.

**D8. "Insights" (module label) vs "AI Insights" (everywhere else).** See **T3**.

**D9. Help's "optional modules" list omits AI Insights and others.** See **T4**.

**D10. `/admin`'s previously-reported dev-server crash could not be re-confirmed or ruled out this pass** (no dev server was running during this static review) — flagging as still unverified rather than resolved, consistent with the earlier audit's own conclusion that it's a local Turbopack tooling issue, not application code. Suggested next step: load `/admin` as an admin user against a running dev server once, specifically to observe the real access-controlled render.

**D11. Overview's "Month-to-date AI spend" cap is built from the non-enforcing "Max active users" field (D2), so the displayed spend/cap ratio isn't a real ceiling.**
Per-user AI budget enforcement actually happens independently per tier; nothing stops total spend from exceeding the displayed cap.
*Fix:* label it "Estimated cap," or tie it to something actually enforced.

### Low

**D12. Module-gated nav items vanish from the sidebar with no inline hint that more exist** — though a real discovery path does exist one hop away (Settings → "Manage features," and the onboarding checklist while it's still visible). A returning user who dismissed onboarding weeks ago has no persistent in-nav cue that more modules exist.
*Fix:* a persistent, low-key "+N more" affordance at the bottom of the nav.

**D13. Templates admin page's visibility disclaimer ("shared with every member, not security") isn't matched anywhere else** — e.g. the Ollama page never notes that its config is server-only/gated. Flagged for asymmetry of care, not a real leak (Ollama's endpoint is confirmed server-only and gated).

**D14. The Usage admin page's "By task"/"By provider" breakdowns show raw internal key strings with no legend** decoding what they mean or which are expected to be high/low volume — legible to a developer-admin, not to a non-technical one.
