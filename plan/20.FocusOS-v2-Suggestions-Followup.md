## 2. Workload's required minutes (1.6 + 1.7 together)

**Before:**

```
required = deep_work block minutes + revision due + assessment prep + course daily share + goal daily share
```

Reading and admin blocks weren't counted, but their focus time was. So a planned reading day read
"Overrun", and a day that skipped its planned reading could still look on track. A goal block was
counted twice: once as a block and once as the goal's daily share.

**After:**

```
required = planned sittings (deep_work, reading, admin: the day score's own set)
         + max(0, revision due − revision-queue sittings)
         + Σ assessments: max(0, prep share − prep sittings for it)
         + Σ courses:     max(0, revision share − revision-bucket sittings of that course)
         + Σ goals:       max(0, goal share − sittings toward it)
```

A sitting counts toward a goal when it has that goal's objective, is goal-bucket work in a linked course,
or has a paper objective for a paper whose `goalId` is the goal.

- A sitting is counted at `sittingPlannedMinutes` (clamped to its length).
- Not counted: tentative blocks, skipped blocks, rescheduled originals, and the locked/fixed layer.
  The locked/fixed layer includes the weekly-planning anchor, a locked admin block. A skip still leaves
  the standing targets in place, so skipping doesn't drive required to zero.
- Non-working day: planned sittings only (as before, but now including reading and admin).
- Day off: 0 (unchanged).
- **One place:** `plannedWorkOf(slots, papers)` in `lib/loadindex.ts` replaces
  `scheduleSummary().plannedDeepWork` at all five callers (dashboard, live hook, workday provider,
  admin day snapshot, morning brief).
- **Stored `Day.loadIndex` snapshots are not rewritten.** Past days keep the number they closed with.

**Consequences:**
- A planned reading day that gets skipped now adds to catch-up hours.
- The on-track streak follows the new number from today on.
- The old day-templates guardrail comment ("reading isn't deep_work so it doesn't inflate required")
  no longer holds. It is rewritten to say why reading counts now.

## 3. Skip and reschedule (1.5)

- New field `ScheduleSlot.rescheduledTo?: { dateKey, slotId }`, set on the original together with
  `status: "skipped"`.
- **`skip_block(date, slotId)`:**
  - For a block that has started or passed and isn't closed.
  - It writes what the wrap-up's "Skipped" button writes.
  - A plain skip still counts in the day score: the plan was missed. It leaves Workload's planned term
    (see §2).
  - A future block is removed with `remove_block` instead.
- **`reschedule_block(date, slotId, toDate?, startTime, endTime?)`:**
  - Places a copy at the new time with the same title, type, objective, tasks, course/bucket and
    sitting numbering, validated like `add_block`.
  - Marks the original skipped and records `rescheduledTo` on it.
  - The original then leaves the day score, Workload's required minutes, the planner's minute
    accounting and the calendar push, since the copy carries the work.
  - The wrap-up stops asking about it.
- **The app:**
  - The wrap-up already excludes skipped blocks.
  - The time grid shows a rescheduled original as skipped, with "Moved to …" in its note.

## 4. Paper → goal link (1.7)

- `Paper.goalId?: string`. The name is distinct from `Paper.goal`, which is the reading-goal text.
  `Goal.linked.paperIds` stays deprecated.
- **`goalWeekPace`** also counts:
  - blocks with a paper objective on a linked paper;
  - sessions whose `paperId` is a linked paper. This includes habit sittings, which pick their paper at
    start.
  - Each session is counted once.
- **Weekly planner:** a linked paper's planned sittings come off the goal's "plan yourself" remainder.
- **Surfaces:**
  - MCP: `update_paper goalId` (refused for a goal that isn't active), `paperView.goalId`, and
    `list_goals` → `linkedPapers`.
  - App: a "Counts toward goal" select on the paper page.
- **Owner data isn't touched.** Linking LithOS/Janus to the Literature goal is the owner's call (one
  `update_paper` each).

## 5. Calendar (1.3, §4)

- **Updates are named.** Each update gives its title, date and what changed (renamed from, moved
  from), using the title and date already stored on the link doc.
- **Task and block are no longer both pushed.** While a non-locked block in the window lists a task,
  that task's due-date event isn't pushed. The first push after deploy removes those task events. They
  were FocusOS-created, so this is allowed, and the push names them. The event comes back if the block
  goes away or passes.
- **Rescheduled originals are not pushed.**
