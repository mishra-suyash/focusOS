## 0. TL;DR

The complaint, verbatim: *"this app is more or less useful for just pomodoro timer, it can't be used for tracking… the tracking is not automated neither the user is able to do much to schedule as courses page and other things are ambiguous."*

That is accurate, and §2 proves each half against the source. The root cause is not a missing feature. FocusOS has thirteen phases of features and **no spine**: every subsystem is individually complete and individually optional, so the only surface that works with zero setup is the one that needs zero setup — the Pomodoro timer. Everything else asks the user to make a decision at the exact moment they were trying to avoid making one.

Two concrete mechanisms behind "tracking is not automated":

1. **Nothing attributes itself.** A focus session only counts toward a course if the user manually picks a task in the timer dropdown, *and* that task has a `courseId`, *and* it has a `bucket`, *and* it has a `dueDate` inside the current week (`lib/courses.ts:115-147`). Four manual conditions in series. Attending a class contributes nothing. A scheduled block contributes nothing. `PomodoroSession.slotId` is written on every session and read by nothing that computes a total.
2. **Nothing has a target set in advance.** Weekly hours are edited four fields at a time on each course card, each with its own Save button, at no particular moment, with no view of whether the week has room for them.

And behind "not able to do much to schedule": planning is **per-day only**. `/plan/day` edits one date. `/plan/calendar` is a read-only month grid. There is no surface anywhere that shows the coming week as a thing you plan, so the user plans nothing and the day arrives empty.

**The fix, in one sentence:** move every recurring planning decision into one scheduled weekly ritual, and make every execution surface read-only and automatic — so that after "Start day" there is nothing left to decide, and the numbers on the course card are produced by working, not by bookkeeping.

## 1. Goals, non-goals, and the rule that governs this pass

**Goals**

- One weekly planning session, at a **fixed time the user sets**, on one page that contains everything that session needs — look back, fixed commitments, hours, block assignment, commit. No tab-switching mid-ritual.
- A focus session **attributes itself** to the block, course, task and bucket it was started inside, without the user picking anything.
- After **Start day**, the next action is always on screen and is always one click. The user never chooses from a list.
- **Random, unplanned work stays in Tasks** and needs no ceremony — capture it, and the next weekly session offers to schedule it.
- The floating widget shows the day and time alongside the current/last focus.

**Non-goals**

- No new AI. Every mechanism here is deterministic, consistent with the codebase's own "no feature is AI-only" rule (README, *AI layer v2*). The weekly planner's block proposals use the existing `nearestFreeGap`/`fillGaps` geometry in `lib/timeline.ts`, not a model call.
- No multi-week or semester-level planning. The horizon is exactly one week, Monday–Sunday, matching `lib/dates.ts`'s existing `weekStartKey`/`weekDates` convention used by every other weekly computation in the app.
- No time-tracking beyond what the app already observes (focus sessions, class logs, schedule blocks). No idle detection, no app-usage monitoring, no manual stopwatch beyond the existing timer.
- No new recurrence engine. `RecurringTaskTemplate` (weekly/biweekly, `lib/recurring-tasks.ts`) already covers recurring commitments and is not touched.
- No retroactive attribution. Existing `PomodoroSession` documents have no `courseId` and will not get one; the new numbers start accumulating from the day Phase 1 ships. Stated openly rather than back-filled with guesses.

**The rule that governs this pass — every new surface must replace one.**

The app's problem is surface count, so a fourteenth phase of pure additions would make it worse. Every section below that adds something names what it demotes or deletes:

| Added | Replaces |
|---|---|
| `/plan/week` (§5) | `/reviews/weekly` — absorbed as its Step 1, page and nav entry deleted |
| Hours table in the weekly session (§5.3) | The four editable hour fields + three Save buttons on every `CourseCard` (§8) |
| "Now" card on Today (§7.2) | `DailyScheduleWidget`'s three-metric grid and duplicate block list |
| Schedule-first `pickNextAction` (§7.1) | The existing first branch order — a replacement inside an existing function, not a second card |
| Auto-attribution (§6) | The timer's "Scheduled for task" dropdown as the *primary* path (it stays as an override) |
| — | The duplicated Recurring-commitments panel on `CourseCard` (§8) |
| — | The Terms panel on `/courses`, moved to Settings (§8) |

## 2. What's broken today, with receipts

### 2.1 Tracking

### 2.2 Scheduling

| Claim | Where it's proven |
|---|---|
| There is **no week-level planning surface** | `app/(app)/plan/layout.tsx` — exactly two tabs, Day and Calendar. `/plan/calendar` (`app/(app)/plan/calendar/page.tsx`) is a month grid whose only action is a link to `/plan/day?date=…`. |

| The morning brief is a **count list, not a sequence** | `lib/dailyloop.ts:48-88` — revisions due, checkpoints in window, papers reading, milestones, external tasks, an alert count, a minutes target. Nothing ordered, nothing actionable. |

### 2.3 "Courses page and other things are ambiguous"

One `CourseCard` (`app/(app)/courses/page.tsx:190-480`) renders, in a single unlabelled vertical stack: status `<select>`, delete, session chips, an "Edit sessions" toggle, four bucket rows (three with their own number input **and their own Save button**), an Assessments list plus a creation form, a Recurring-commitments list plus a creation form plus a "Generate now" button, a Papers/Open-tasks/Linked-goals grid, a class-log form, and a topics list. Seven independent write paths on one card, with three separate Save buttons that each mean something different.

Worse, the Recurring-commitments panel is **duplicated verbatim** on `/tasks` (`app/(app)/tasks/page.tsx:129-178`) — two places to create the same object, each with its own "Generate now".

And the four bucket rows are the "ambiguous" complaint in its purest form: `revision` writes `Course.targetMinutesPerWeek`, `assignment`/`backlog` write `Course.weeklyTargets`, and `goal` is read-only and derived from linked Goals divided by their course count (`lib/courses.ts:96-111`). Four rows that look identical, three storage locations, one of which is not editable at all, with no explanation of when you're supposed to touch them.

## 3. Scenarios — what "it works" actually looks like

Five walkthroughs. Each ends by naming the section that makes it true. These are the acceptance narrative for the whole pass.

### S1 — Sunday 18:00: the weekly planning session

The user set this time once, in Settings. At 18:00 a locked **"Weekly planning"** block is already on Sunday's timeline (it has been there all week, visible in `/plan/day` and on the calendar), and the Today page's Now card says *Weekly planning · 18:00–18:30 · Open the week*. One click lands on `/plan/week`.

The page opens on **Look back** — last week's numbers, nothing to fill in: 11h 20m done against 14h planned, three days on-track and two behind, 4h catch-up, two classes logged out of three, one paper untouched for 16 days, and five tasks that were due last week and are still open.

Scrolling (or pressing Continue) reaches **The week already contains** — a seven-column grid of next week with every fixed thing already drawn: six class sessions, sleep/meals/gym from routine, the Thursday TA meeting from its recurring template, one checkpoint due Friday, one imported Google Calendar event. Above it: *Next week has 39h 15m free inside your working hours (Mon–Sat, 09:00–18:00).*

**Set this week's hours** is one table, not four cards: a row per active course, four numeric columns, one Save for the whole table. As numbers are typed, the header meter moves — *Committed 28h 30m of 39h 15m free* — and turns amber past 85%. This is the first time in the app's life the user sees "you are asking for more than the week has" **before** the week starts.

**Assign the week** proposes 23 blocks, laid into the free gaps: four 50-minute CS201 revision blocks (Tue/Wed/Fri/Sat), two checkpoint-prep blocks on Wed and Thu before Friday's quiz, a 45-minute revision-queue block each weekday morning, two reading blocks for the stale paper, and the five slipped tasks from Look back placed where they fit. The user dismisses two, drags one from Tuesday to Wednesday, hits **Accept all**. Seven `DailySchedule` documents are written.

**Commit** saves the plan onto `weeklyReviews/{monday}` and stamps `completedAt`. Elapsed: about eight minutes. → §5

### S2 — Monday 08:30: Start day

The user clicks **Start day**. Today's schedule already exists (S1 wrote it), so nothing is generated and no template question is asked. The Today page shows exactly one thing at the top:

> **Now · 08:30–09:20 · Deep work — CS201 revision**
> 50 min remaining · *Start focus* ▸
> Next: **CS201 lecture** at 09:30

They press *Start focus*. The timer is already labelled "CS201 revision", category `reading`, linked to the block, the course, and the bucket. They did not open a dropdown. → §6, §7

### S3 — Monday 09:30: the class block

The lecture block begins. A notification fires: *CS201 lecture starting.* The Now card switches to it and its primary action is **Log this class**, not *Start focus* — a class is attended, not focused-on.

At 10:50 the block ends. The Now card asks the one question worth asking: *Did you attend CS201?* One tap on **Attended** writes the class log for the date and the block's 80 minutes land on the course's **Class time** row. The 50 minutes of focus from S2 land on its **Revision** row. Neither required creating a task. → §6.3, §8

### S4 — Wednesday 14:10: something unplanned arrives

An advisor asks for a literature summary by next Monday. The user opens **Tasks**, types the title, presses Enter. No course, no bucket, no estimate, no block. It sits in Inbox.

Today's plan does not change and nothing is re-shuffled — mid-week replanning is exactly the thinking the weekly ritual exists to remove. On Sunday, the task appears in **Assign the week**'s "Unscheduled backlog" list with a proposed two-block placement. → §9, §5.4

### S5 — Friday 09:00: a week that was never planned

The user skipped Sunday. Start day finds no schedule and falls back to today's default template plus class and routine blocks, exactly as it does now. The Now card is honest about it:

> **No plan for today.** Your last weekly planning session was 12 days ago.
> *Plan this week* ▸ · or *Use my workday template* ▸

"Up next" then falls through to its existing cascade — checkpoint prep, revision queue, top task — so the app is never worse than it is today. The failure mode is a visible prompt, not an empty screen. → §7.3

## 4. Data model changes

Four optional scalars on two existing interfaces, plus three optional sub-objects on settings and the weekly review. No collection is added, nothing is migrated, and every existing document stays valid.

```ts
// types/index.ts — ScheduleSlot, additive
export interface ScheduleSlot {
  // ...existing fields unchanged...
  /** Which course this block belongs to. Set by `courseSlotsForDate` on a class block and by the
   *  weekly planner on a course-bucket block. Absent on every block that exists today, and on any
   *  block that genuinely isn't course work. This is what lets a focus session started inside the
   *  block credit the course without matching on the title string. */
  courseId?: string;
  /** Which of the course's four weekly planning buckets this block counts against. Only meaningful
   *  alongside `courseId`; absent on a class block (class time is not a planned bucket — see §6.3). */
  bucket?: TaskBucket;
}

// types/index.ts — PomodoroSession, additive
export interface PomodoroSession {
  // ...existing fields unchanged...
  /** Copied from the block/task this session was started against, at finalize time. The single
   *  field that turns `completedMinutesThisWeek` from an estimate into a measurement (§6.4). */
  courseId?: string;
  bucket?: TaskBucket;
}

// types/index.ts — UserSettings, additive
export interface UserSettings {
  // ...existing fields unchanged...
  /** The "fix a admin time" ask: when the weekly planning session happens. Absent = the feature is
   *  off and nothing is materialized, same "absent means the default" convention `routineBlocks`
   *  already uses. */
  weeklyPlanning?: {
    enabled: boolean;
    /** 0 (Sun) – 6 (Sat) — same convention as `RoutineBlock.daysOfWeek` and `CourseSession.dayOfWeek`. */
    dayOfWeek: number;
    startTime: string;
    endTime: string;
  };
  /** The hours the user actually intends to work. Absent = `DEFAULT_WORKING_WINDOW` (09:00–18:00,
   *  Mon–Sat). Two readers: the capacity meter's denominator (§5.3) and the weekly planner's block
   *  placement bounds (§5.4) — without it, "free time" means every waking minute, which is not a
   *  number anyone plans against. */
  workingWindow?: { startTime: string; endTime: string; daysOfWeek: number[] };
}

// types/index.ts — WeeklyReview, additive
export interface WeeklyReview {
  // ...existing wins/missedGoals/blockers/nextWeekPriorities unchanged...
  /** The forward half of the weekly document. `weeklyReviews/{weekStart}` is already keyed by the
   *  Monday of its week, so the plan for a week and the review of it belong on one document — the
   *  same "one read renders the whole period" reasoning that produced the merged `Day` doc. */
  plan?: WeekPlan;
}

export interface WeekPlan {
  /** Snapshot of what was committed, so a later target edit never silently rewrites history. */
  targets: { courseId: string; bucket: TaskBucket; minutes: number }[];
  /** Capacity numbers as computed at commit time (§5.3) — kept so Look back can compare plan to reality. */
  capacity: { freeMinutes: number; committedMinutes: number };
  /** The blocks offered in Step 4 and what happened to each, keyed by index — exactly the
   *  `EveningRollup.slotDecisions` pattern, so a re-opened planner never re-offers a handled proposal. */
  proposedBlocks: (ProposedSlot & { dateKey: string; courseId?: string; bucket?: TaskBucket })[];
  blockDecisions?: Record<string, ProposalDecision>;
  completedAt?: string;
}
```

**On `UserSettings.dayStartTime`.** It already exists (`types/index.ts:806`) and is **dead**: written once by `components/onboarding-flow.tsx:106` and read by nothing — `TemplateGallery`'s day-start input is its own local state (`components/template-gallery.tsx:38`), not the setting. `workingWindow.startTime` supersedes it and gives the concept its first real reader; leave `dayStartTime` in place, unread, rather than migrating it.

**On writing `plan` alongside the review fields.** Verified: `saveWeeklyReview` already uses `setDoc(..., { merge: true })` (`lib/firestore.ts:257-262`), so Step 1's "Save weekly check-in" — which never includes a `plan` key — cannot clobber Step 5's plan, and vice versa. Two consequences to respect in the implementation: `plan.blockDecisions` **deep-merges** (a decision is never lost, which is what we want), while `plan.proposedBlocks`, being an array, is **replaced wholesale** on every write (so Step 4 must always write the complete list, never a delta).

**Why `Course.targetMinutesPerWeek` / `weeklyTargets` are kept and not replaced.** They stay the live "current target" the course card reads, and `WeekPlan.targets` is the per-week snapshot. Today, editing a course's hours in week 6 silently changes what `bucketWeeklyTarget` reports for weeks 1–5 too, because there is only one number. Keeping both fixes that without touching the existing readers — `planRevisionTemplateSync` and `courseTargetMinutesForDay` keep working unchanged.

**What is deliberately not added:** no `weekPlans` collection (it would duplicate a document already keyed by Monday); no `Task.weekKey` (a `dueDate` inside the week already says it); no `ScheduleSlot.actualMinutes` (derivable from sessions, and a stored duplicate would drift); no `classMinutes` field (derivable from the class block's duration plus the log's attendance — see §6.3).

## 5. `/plan/week` — the weekly planning session

A third tab in `app/(app)/plan/layout.tsx`, **first** in the list: `Week · Day · Calendar`. Route `app/(app)/plan/week/page.tsx`, `?week=yyyy-MM-dd` (a Monday key, defaulting to the coming week if today is within the planning window, else the current week).

One scrolling page, five numbered sections, a sticky header carrying the capacity meter and a **Commit** button. Not a wizard with hidden steps — "that page should be complete and contain everything it needs" means everything is visible and re-reachable at once.

### 5.1 Step 1 — Look back (zero inputs)

Everything here already exists somewhere in the app and is simply assembled in one place:

- Planned vs. done per course bucket for the **outgoing** week (`scheduledMinutesThisWeek`/`completedMinutesThisWeek` with an explicit `weekDateKeys` argument — both already accept one, `lib/courses.ts:130,145`).
- The Workload chip row and catch-up hours — lifted verbatim from `/reviews/weekly` (`app/(app)/reviews/weekly/page.tsx:81-95`).
- Goals section — lifted verbatim from the same page (lines 97-128), including "Mark reviewed".
- The four free-text fields (wins / missed / blockers / next-week priorities) — same writer, `saveWeeklyReview`.
- **New, and cheap:** classes held vs. logged (`courseSlotsForDate` per date vs. `classLogs` docs — this finally fills the `unloggedClasses: []` gap `lib/dailyloop.ts` has documented as deferred since Phase 6), papers in `reading` untouched 14+ days (the same rule `lib/ai/triage.ts` already uses), and tasks that were due last week and are still open.

**`/reviews/weekly` is deleted**, its nav entry removed, and `next.config.mjs` redirects it to `/plan/week`. The `weeklyCheckin` module id is retained and now gates Step 1's review half rather than a whole page (see §13).

### 5.2 Step 2 — The week already contains (zero inputs)

A seven-column grid of the coming week, every fixed commitment drawn, each computed by a pure function that already exists:

| Layer | Source |
|---|---|
| Class blocks | `courseSlotsForDate(courses, dateKey)` — `lib/courses.ts:15` |
| Routine anchors | `routineSlotsForDate(settings.routineBlocks ?? DEFAULT_ROUTINE_BLOCKS, dateKey)` — `lib/routine.ts:44` |
| Recurring commitments | `isTemplateDueOn(template, dateKey)` — `lib/recurring-tasks.ts:10` |
| Checkpoints due / in prep window | `useCourseCheckpoints`, the same window rule as `buildMorningBrief` |
| Already-saved blocks | existing `dailySchedules` for those dates |
| Google Calendar imports | `ScheduleSlot.type === "external"` on those dates |
| The planning anchor itself | §5.6 |

Read-only, with a "fix this" link per layer (course → `/courses`, routine → `/settings/routine`, commitment → `/tasks`). Nothing is editable here; this is the constraint set the next two steps plan against.

### 5.3 Step 3 — Set this week's hours (the only input surface for targets)

One table. Rows = active courses (`effectiveCourseStatus === "active"` for any date in the week, not just today). Columns = the four buckets, with the same `InfoHint` copy the course card uses today so no explanation is lost. The `goal` column stays derived and read-only, as it is now (`bucketWeeklyTarget`, `lib/courses.ts:107-109`), with the linked goals named in the cell so its read-only-ness is finally explained instead of just being inert.

A final row for non-course commitments: the revision queue's projected minutes for the week (`estimatedReviewMinutes` × 7, `lib/revision.ts`) and each active goal's `targetHoursPerWeek` not already attributed to a course.

**One Save for the whole table**, writing `Course.targetMinutesPerWeek` / `Course.weeklyTargets` and calling the existing `syncRevisionTemplate` once per changed course — the same function the course card calls today (`lib/courses.ts:67`), so the auto "Revise <course>" recurring template keeps staying in sync with zero new logic.

**The capacity meter** is the genuinely new idea and lives in the sticky header:

```
free      = Σ over each day in workingWindow.daysOfWeek of
              (minutes between workingWindow.startTime and endTime
               that no Step 2 layer already claims)
committed = Σ bucket targets + checkpoint prep owed + projected revision minutes
```

**`free` is deliberately not "the week minus what's booked".** That formula — 7 × 1440 minus the drawn layers — yields ≈89h against the default routine blocks, because it counts 03:00 on a Tuesday as available working time. A meter that opens at *28h 30m of 89h* tells the user they have room to spare, which is the exact opposite of the confrontation this step exists to produce. Capacity is the hours you intend to work, minus what those hours already contain.

Worked example with the defaults, which is where S1's number comes from: `DEFAULT_WORKING_WINDOW` is 09:00–18:00 on Mon–Sat = 9h × 6 = **54h**. A week containing six class sessions inside the window (≈8h), the default lunch routine block 12:30–13:15 on those six days (4h 30m), a Thursday TA meeting (1h) and one imported calendar event (1h 15m) leaves **39h 15m free**. Committing 28h 30m against that is 73% — under the amber line, and a number that means something.

Rendered as `Committed 28h 30m of 39h 15m free`, amber past 85%, red past 100%. It reuses the Workload's band vocabulary but answers the opposite question: the Workload tells you what today asked of you after the fact; this tells you whether the week can hold what you're about to promise it. Pure function `weekCapacity(...)` in a new `lib/weekplan.ts`, unit-tested by `scripts/verify-weekplan.ts` alongside the other `verify:*` scripts.

The working window is editable inline in this step's header (it is a planning input, and the first week will be the week the user discovers their real one), persisting to `UserSettings.workingWindow`.

### 5.4 Step 4 — Assign the week

The planner proposes blocks and the user accepts, edits, or dismisses them. **Nothing is ever auto-applied** — the same rule Phase 6's evening rollup already established for proposals, and the same `ProposalDecision` bookkeeping so a re-opened planner never re-offers something handled (`types/index.ts:678,700-701`).

Proposal sources, in priority order:

1. **Checkpoint prep** — each `requiresPrep` checkpoint's `prepEstimateMin` split across its `prepLeadDays`, placed on the days inside the window. Directly reuses `buildProposedSlots`' existing logic (`lib/dailyloop.ts:163`), lifted from one day to seven.
2. **Course buckets** — each bucket's weekly target, split into `workMinutes`-sized chunks (the same sizing `planRevisionTemplateSync` uses, `lib/recurring-tasks.ts:96`), distributed across the week's days with the fewest existing commitments. Each proposed block carries `courseId` **and** `bucket` — this is what makes §6's attribution work without the user ever touching a task.
3. **Revision queue** — one block per weekday, sized by `estimatedReviewMinutes`.
4. **Unscheduled backlog** — open tasks with no `dueDate`, plus tasks whose `dueDate` fell in a past week (S4's path). Sized by `taskBlockMinutes` (`lib/timeline.ts:224`), carrying `assignedTaskIds`.
5. **Stale papers** — `status === "reading"`, untouched 14+ days, one reading block.

Placement uses `nearestFreeGap` (`lib/timeline.ts:68`) against that date's existing + already-accepted blocks, per day, **bounded to `workingWindow`** — the same bounds the capacity meter measures against, so the meter can never promise room the planner then can't place a block in. A proposal that finds no gap is shown in a **"Didn't fit"** list with its reason — never silently dropped, the same honesty rule `fillGaps` follows and the same one the highlight pipeline follows for unmatched quotes.

Controls: **Accept all** · per-day Accept · per-block Edit (time/day) and Dismiss. Accept writes real `DailySchedule` documents through the existing `saveDailySchedule`, validated by the existing `validateSlots` before every write — a proposal set that would produce an overlap is refused as a set, not partially committed (the same all-or-nothing discipline `shiftRestOfDay` already applies, `lib/timeline.ts:373`).

### 5.5 Step 5 — Commit

Writes `weeklyReviews/{weekStart}.plan` with the targets snapshot, the capacity numbers, the proposal list and its decisions, and `completedAt`. Sets the Today page's "last planned" state, which is what S5's fallback prompt reads.

### 5.6 The fixed admin time

`UserSettings.weeklyPlanning` (§4), edited on `/settings/routine` next to the routine blocks it behaves like — because it is materialized the same way:

```ts
// lib/weekplan.ts — mirrors routineSlotsForDate/courseSlotsForDate in shape: pure, no Firestore.
export function weeklyPlanningSlotForDate(
  setting: UserSettings["weeklyPlanning"],
  dateKey: string
): ScheduleSlot | null
```

Returns a locked (`locked: true`, `type: "admin"`) slot with the stable id `weekly-planning` when the date's day-of-week matches, else null. Three call sites merge it in alongside the class and routine slots, each already doing exactly this for two other layers:

- `components/workday-session-provider.tsx:161-164` (Start day's `lockedSlots`)
- `app/(app)/plan/day/page.tsx:74-80` (`wantedLockedSlots`)
- `app/(app)/plan/calendar/page.tsx` (the month grid's per-day computation)

**Why a dedicated setting rather than a `RoutineBlock` the user adds by hand:** a routine block is a personal anchor (sleep, meals, gym) with no behavior attached; this one needs to link to `/plan/week`, drive the "you haven't planned in N days" prompt, and be findable by the Now card. Routing it through `routineBlocks` would mean matching on a label string. **Why not a timed `RecurringTaskTemplate`:** `10.FocusOS-v2-Connected-Flow-Plan.md`'s implementation-status line records that the timed-commitment → `ScheduleSlot` materialization (its §4.4 / Phase 3) was deliberately cut, so a timed template produces a task and no block. The routine pathway is the only one that already puts a locked block on the timeline. See §13 for the "should it be visible in the routine list anyway" question.

## 6. Automatic attribution — the tracking fix

This is the smallest and highest-value part of the pass, and it ships independently of everything else (§11, Phase 1).

### 6.1 Blocks learn which course they belong to

`courseSlotsForDate` gains one line: `courseId: course.id` on the slot it builds (`lib/courses.ts:24-33`). The weekly planner sets `courseId`+`bucket` on the blocks it proposes. `createTaskBlock` (`lib/timeline.ts:326`) copies `task.courseId`/`task.bucket` onto the block it creates from a task. Nothing else changes; `resyncFutureClassSlots` already regenerates class slots from the same function, so existing future schedules pick the field up for free on the next course edit.

### 6.2 The timer reads the block you are in

A new hook, `hooks/use-focus-context.ts`, composes what already exists: today's `DailySchedule`, `useCurrentMinute()` (`hooks/use-current-minute.ts`), and `getActiveSlot` (`lib/schedule.ts:155`). `FocusSessionProvider` consumes it and, **while no session is running and the user has not overridden anything**, keeps `label`, `category`, `slotId`, `courseId`, `bucket` and `taskId` in sync with the active block:

- `label` ← block title; `category` ← `categoryForSlotType(block.type)` (`lib/timeline.ts:355`)
- `slotId`/`courseId`/`bucket` ← the block's own fields
- `taskId` ← the block's `assignedTaskIds` **only when there is exactly one** — the same disambiguation rule the existing `?startFocus=1` path already applies (`app/(app)/dashboard/page.tsx:121-124`)

Manual choice always wins, generalizing the existing `labelTouched` flag (`components/focus-session-provider.tsx:90-98`) into a `contextTouched` flag reset the same way — per finished session, and only when nothing is still linked. The timer's task `<select>` stays exactly where it is; it stops being the only way in.

`finalizeSession` writes `courseId`/`bucket` onto the `PomodoroSession` alongside the existing `taskId`/`slotId`, and keeps the existing `MIN_MINUTES_FOR_TASK_CREDIT` floor unchanged.

### 6.3 Class time counts itself

A class block's duration is real course time, but it is not focus time and must not be mixed into a focus-minute total. It becomes its own read-only row, **Class time**, on the course readout, computed by a pure function:

```ts
// lib/tracking.ts
classMinutesForWeek(courseSlotsByDate, classLogs, weekDateKeys): number
```

Sums the duration of each class block on a date whose `ClassLog` for that course records `attendance === "attended"` (or `"self_study"`). No new field: `ClassLog` already exists per course per date, and the block duration is already on the schedule. A class with no log counts zero and shows as *2 of 3 logged* — which is also the signal Step 1 needs, and the same one `lib/dailyloop.ts` has had stubbed as `unloggedClasses: []` since Phase 6.

`ClassLog.durationMin` — in the type and the writer, with no UI and no reader (§2.1) — becomes the override for the case where the class ran long or short. That is the honest use for a field that is currently dead.

### 6.4 Course numbers become measurements

`completedMinutesThisWeek` is rewritten to take sessions instead of tasks:

```ts
// lib/courses.ts — same name, new inputs
completedMinutesThisWeek(sessions, courseId, bucket, weekDateKeys): number
```

Summing **real `PomodoroSession.minutes`** for work-mode sessions completed in the week where either the session carries `courseId`+`bucket` directly, or its `taskId` resolves to a task carrying them. `scheduledMinutesThisWeek` is unchanged — "planned" is legitimately an estimate.

Callers: the course card (§8) and Step 1. `Task.completedPomodoros` stays exactly as it is — it is a per-task counter with its own honest meaning ("sessions left" on a task) and is not the right unit for a weekly course total.

### 6.5 Blocks complete themselves — carefully

**What this deliberately does not do:** mark a block `completed` because its end time passed. `13.FocusOS-v2-UI-Coherence-Audit.md` A9 specifically fixed that bug — `computeSlotStatus` returning `"completed"` for a merely-elapsed block once made a day where nothing happened read as "100% complete", which is why `DailyScheduleWidget` now renders the word "past" instead (`components/daily-schedule-widget.tsx:147-152`). Re-introducing it would make the numbers *more* automatic and *less* true.

Instead, coverage:

```ts
// lib/tracking.ts — pure
slotCoverageMinutes(slot, sessions): number   // sessions whose slotId matches, clamped to the block
slotAutoStatus(slot, sessions, threshold = 0.6): "completed" | null
```

A block flips to `completed` when focus sessions logged against its `slotId` cover at least 60% of its duration; a class block flips when its log says attended. Everything else stays **past**, and the day wrap-up asks about it — one row per uncovered past block, *Done / Skipped*, one tap each.

That question list goes in **both** wrap-up surfaces, as one shared component: `/reviews/daily` (`app/(app)/reviews/daily/page.tsx`) and `DayWrapupSheet` (`components/day-wrapup-sheet.tsx`), which is the in-place sheet End day opens instead when the `weeklyCheckin` module is off (`components/day-session-bar.tsx:53-57`). Building it into only one means half the users silently never get asked, and their blocks stay `past` forever.

That is the honest automation: the app fills in what it observed and asks about what it did not.

Run at two points, both existing: after `finalizeSession`, and inside `end()` before the Workload snapshot is computed (`components/workday-session-provider.tsx:187-225`) — which means `scheduleSummary`'s `completedDeepWork` is finally non-zero and the Workload's `actual` term stops under-counting planned work that genuinely happened.

## 7. The automatic day

### 7.1 "Up next" becomes schedule-first

`pickNextAction` (`lib/next-action.ts`) gains one input, `activeSlot`/`nextSlot`, and one new **first** branch:

1. **A block is active right now** → that block is the next action. `why` is its remaining time; the primary action is *Start focus* (pre-filled per §6.2), or *Log this class* for a class block, or *Open paper* / *Review* when the block carries a paper or revision reference.
2. **A block starts within 15 minutes** → *Next: X at HH:MM*, with the same action pre-armed.
3. **The day has a plan but nothing is active** (a gap) → fall through to the existing cascade, unchanged.
4. **The day has no plan at all** → S5's prompt (§7.3).

Everything below branch 1 is the current function, untouched. This is a replacement of the cascade's entry point, not a second card.

### 7.2 One "Now" card replaces the schedule widget's metric wall

Today's dashboard middle column renders `DailyScheduleWidget` in compact mode: a three-metric grid, a day-progress bar, a block strip, a current-block panel, a next panel, a completion count, and up to four upcoming blocks — much of which the Now card and the Workload widget already say.

The Now card is: current block (title, type chip, elapsed/remaining bar), its assigned tasks as checkboxes, **one** primary action, and a single *Next: X at HH:MM* line. The full-day list collapses under it behind *Show the whole day*. The three-metric grid and the duplicate current/next panels are deleted, not hidden — `dayProgressPercent` in particular ("Day complete 43%") measures wall-clock, not work, and has never meant anything actionable.

### 7.3 Start day actually starts the day

Three additions to `WorkdaySessionProvider`, all inside machinery that already exists:

- **Block transitions.** The 30-second reminder interval (`workday-session-provider.tsx:101-119`) gains a third check: when `getActiveSlot` changes, fire a notification for the new block and run §6.5's auto-status pass on the one that ended. Same `fireReminder` plumbing, same permission, no new timer.
- **The no-plan prompt.** When Start day finds no schedule and no weekly plan for the current week, `startDayNotice` (which already exists and already renders through `StartDayNoticeBanner`) carries S5's two-option message instead of today's template-fallback text.
- **Auto-arm the timer.** After a successful start, set the focus context from the current block (§6.2) without starting the countdown — so the first *Start focus* click is genuinely one click.

### 7.4 What the morning brief becomes

`buildMorningBrief` stays deterministic and stays exactly as it is. `MorningBriefCard` re-renders it as the day's **sequence** rather than a count list: the blocks in order with their attached commitments, with the existing counts folded in as annotations on the blocks they belong to. No new data, no new writer.

## 11. Phasing

Each phase is independently shippable and independently useful. The order matters: Phase 1 makes the numbers real, Phase 2 gives them targets, Phase 3 makes the day run itself, Phase 4 removes what the earlier phases replaced. **Phase 4 must not ship before Phase 2** — demoting the course card's hour fields before `/plan/week` exists would leave nowhere to set hours at all.

1. **Phase 1 — Automatic attribution + the PiP clock.** §4's four scalars on `ScheduleSlot`/`PomodoroSession`, §6.1–§6.5, §10. No new page, no new route.

   **What Phase 1 does and does not deliver, precisely.** It replaces nominal minutes with measured ones everywhere, makes class attendance count for the first time, and gives `scheduleSummary` a real `completedDeepWork`. It does **not** on its own dissolve §2.1's four-condition chain for the three *planned* buckets, because in Phase 1 the only blocks carrying `courseId` are class blocks (which feed Class time, not a bucket) and task-derived blocks (which already resolved through `taskId`); course-and-bucket-tagged work blocks are produced by the weekly planner in Phase 2.

   To let Phase 1 stand alone anyway, it also adds a **course + bucket picker to `BlockInspector`** (`components/plan/block-inspector.tsx`, inside the existing `MoreOptions`, rendered only when the user has courses — the same conditional `TaskForm`'s course select already uses). A few lines, and it means a hand-made deep-work block can be tagged today and attribute itself for the rest of the week, with or without Phase 2.
2. **Phase 2 — The weekly session.** §5 in full, `WeeklyReview.plan`, the `/plan/week` route and the nav/tab change, `/reviews/weekly` absorbed and redirected, the §5.6 admin-time anchor.
3. **Phase 3 — The automatic day.** §7.1's schedule-first `pickNextAction`, §7.2's Now card, §7.3's block transitions and no-plan prompt, §7.4's brief re-render, and the day wrap-up's uncovered-block questions.
4. **Phase 4 — The demotions.** §8 in full, §9's backlog surfacing.

## 12. Acceptance criteria

Checkable, and mostly checkable without a browser:

1. Start a focus session from the Today page during a planned course block, with **no dropdown touched**: the saved `PomodoroSession` carries `slotId`, `courseId` and `bucket`, and the course card's bucket row moves by the session's **real** minutes. (§6)
2. Attend a class and log it: the course's **Class time** row moves by the block's duration; no task was created. (§6.3)
3. A 50-minute deep-work block with 35 minutes of sessions against it reads **completed**; one with 10 minutes reads **past** and is asked about in the day wrap-up. Neither happens from the clock alone. (§6.5)
4. End day: `scheduleSummary(...).completedDeepWork` is non-zero on a day where planned deep work actually happened. (§6.5)
5. `/plan/week` for a week with three active courses, six class sessions and one checkpoint renders Steps 1–2 with **zero** user input, and the capacity meter's `free` equals the working window's total minutes (54h on the defaults) minus only the Step 2 minutes that fall **inside** that window — a 23:00 sleep block and an 08:00 commute change it by nothing. (§5.2, §5.3)
6. Accepting all of Step 4's proposals writes `DailySchedule` documents that pass `validateSlots` on every affected date, and re-opening the planner re-offers none of them. (§5.4)
7. With `weeklyPlanning` enabled, the anchor block appears on that weekday in `/plan/day`, in the month grid, and in a freshly-started day, and cannot be dragged or deleted. (§5.6)
8. Start day on a planned day: the Today page's first card names the current block and its one action, with no list to choose from. (§7.1, §7.2)
9. Start day with no plan and no weekly plan: the prompt from S5 appears and "Up next" still produces its existing cascade result. (§7.3)
10. The PiP widget shows `Mon · 14:32` right-aligned in the current-focus card, at the unchanged 320×420 default, and the minute advances without reopening. (§10)
11. Every existing document still loads and every default holds: a `PomodoroSession` with no `courseId`, a `ScheduleSlot` with no `courseId`, a `WeeklyReview` with no `plan`, a `UserSettings` with neither `weeklyPlanning` (no anchor materialized anywhere) nor `workingWindow` (falls back to `DEFAULT_WORKING_WINDOW`). Saving the Step 1 review fields leaves an existing `plan` intact, and saving a plan leaves the review fields intact. (§4)

New pure-function verify scripts, matching the existing `scripts/verify-*.ts` convention: `verify-weekplan.ts` (`weekCapacity` — including a block wholly outside the window, one straddling its edge, and a non-working day; proposal placement inside the window bounds; `weeklyPlanningSlotForDate` including the day-of-week and disabled cases) and `verify-tracking.ts` (`slotCoverageMinutes`, `slotAutoStatus` at and around the threshold, `classMinutesForWeek` across each attendance value, `completedMinutesThisWeek` via both the direct and the task-resolved path).

## 13. Open questions — real product decisions, flagged rather than assumed

- **Should the weekly planning anchor also appear in `/settings/routine`'s block list?** §5.6 routes it through a dedicated setting so it can carry behavior a routine block can't. But it will look exactly like a routine block on the timeline, and a user who wants to move it will look for it in the routine list first. Leaning toward: show it in that list as a special, non-deletable row that links to its own editor.
- **Is a derived working window the right denominator, or should the user just declare a number?** §5.3 derives `free` from a window minus what's booked. The simpler alternative is to have the user state "I intend to work 35h this week" in Step 3 and measure commitments against that — no geometry, no new field, and a promise rather than a derivation the user can argue with. The derived version was chosen because Step 4 has to place blocks in real gaps anyway, so meter and placement share one set of bounds and can never disagree. Worth a second opinion before Phase 2 builds on it.
- **Is 60% the right auto-complete threshold (§6.5)?** Alternatives: any session against the block completes it (more automatic, more false positives on a block you abandoned after five minutes), or 80% (fewer false positives, more wrap-up questions). 60% is a starting guess, not a derived number — worth one week of real use before fixing.
- **What happens to the `weeklyCheckin` module id when `/reviews/weekly` is absorbed?** A user on a pack with it off currently loses a nav entry and a page. After §5.1 they would instead lose Step 1's review half while keeping Steps 2–5. That seems right — planning is more core than reviewing — but it changes what an existing toggle means, which is the kind of thing that should be decided, not inherited.
- **Should a missed weekly planning session block anything?** Currently: no, it only prompts (S5). A stronger version would make Start day open the planner on a Monday when the week is unplanned. That is more "automatic" and also more coercive; it deserves an explicit yes rather than a default.
- **Class time vs. focus time in the Workload.** §6.3 keeps class minutes out of the focus-minute total, so they do not currently reach the Workload's `actual` term either — meaning a day of four lectures still reads as "behind". Arguably attended class time should count toward `actual`. Deliberately not changed in this pass, because it would shift every historical Workload comparison; flagged as the single highest-value follow-up if the bands start reading wrong.
- **Per-week target history.** §4 keeps both the live `Course.targetMinutesPerWeek` and a per-week snapshot in `WeekPlan.targets`, which means the course card and Step 1 can disagree about "the target" for a past week. The alternative — `bucketWeeklyTarget` reading the week's snapshot when one exists and falling back to the course — is cleaner but touches a function three other callers already depend on. Worth deciding before Phase 2 rather than after.
- **Does anything reconcile a week the user re-plans mid-week?** Today's answer: re-running `/plan/week` for the current week re-offers only undecided proposals, and already-written blocks stay. That is the conservative behavior; whether a mid-week replan should be able to clear the rest of the week and start over is not settled.
