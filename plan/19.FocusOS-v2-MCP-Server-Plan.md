# FocusOS v2 — An MCP server, so Claude can see and change FocusLab

**Status:** Phases 0–5 built 2026-11-27 (uncommitted, on `fix/reader-refinements`); Phase 6 not built (D3). Verified on localhost with the test account; the claude.ai connection (criteria 10, 15 on a phone) needs a public HTTPS URL and hasn't been run. Originally written 2026-11-27 against `6f25adc`.

**Built differently from this plan, and why:**
- **Decisions:** D1–D6 taken as recommended. D2 is two admin switches: `mcpEnabled` (kill switch) and `mcpMembersAllowed` (members too; owner and admin always). Both default off.
- **A never-planned day (§5.2):** `add_block` builds it the way `/plan/week`'s `daySlotsWithFixed` does (classes, commitments, routine, planning anchor), **not** from the default template. In the app a template lands only through Start day or an explicit Apply; applying it here would drop a whole template onto a day when Claude adds one block.
- **Side effects the plan didn't list, now mirrored:** completing a task, moving an assessment to submitted/done/missed, a goal leaving active and a milestone ticked done all release unstarted future sittings (`useReleaseSittings`). `log_class` runs the full `saveClassLogEntry` flow (topics, first revision cards, catch-up task for a missed class).
- **Pure modules split out for the server:** `lib/courses-sync.ts` (the Firestore half of `lib/courses.ts`), `lib/checkpoints.ts` (type defaults), `lib/classlog-plan.ts` (topic split and revision seed).
- **§2.4 was not true of the code:** the two-tab guard showed its banner but still autosaved the stale copy over the other writer. `useDayAutosave` now holds writes while the conflict is open (status "Not saved: choose Reload or Keep mine"). So that this tab's own writes by other paths (a sitting closing itself in the focus timer, Start day, a released sitting) don't trip it, `saveDailySchedule` records each write's stamp per date (`ownScheduleStamp`) and the editor quietly adopts its own tab's write when it has nothing unsaved. Before, those writes raised a false "another tab" banner and the next edit overwrote them (a closed sitting's "completed" status, for example).
- **Open:** after Reload, Undo still steps back to the pre-conflict copy (`resetUndoState` keeps history, by design per `verify-undo-stack`); the deployed rules let a client write its own `users/{uid}/mcpActivity`; Google `signInWithRedirect` wasn't added (authDomain is `*.firebaseapp.com`, which breaks redirect sign-in on Safari/iOS); email/password and email-link are the mobile path.

## 0. TL;DR

**The brief:** "make a plan to enable an MCP server that I will connect to my Claude, so that it can see and also make changes if possible. It should have the whole context."

**Assumption:** "whole context" means **all of your FocusLab data**: tasks, schedules, courses, papers, goals, focus history, reviews and settings. It also means the meaning of that data: the vocabulary, the derived numbers and the rules. It does not mean the source code, which Claude Code already reads.

**The plan, in five ideas:**

1. **One remote MCP server inside the existing Next.js app,** at `https://<prod-domain>/api/mcp`.
   - It uses the Streamable HTTP transport and is stateless.
   - It is deployed to Vercel like everything else.
   - It reads and writes Firestore through the Admin SDK that the crons already use.
   - A remote server works from claude.ai, Claude Desktop, Claude mobile, Cowork and Claude Code **[docs]**.
2. **FocusLab becomes its own small OAuth 2.1 server.**
   - Your claude.ai account can't use a static API key. Claude's "request headers" auth is a beta limited to some organisations **[docs]**.
   - So claude.ai needs OAuth, with Claude registering itself through a Client ID Metadata Document (CIMD) or through Dynamic Client Registration (DCR).
   - The sign-in step reuses the existing Firebase login, so you approve Claude from a FocusLab screen.
   - Phase 1 starts with a **personal access token** instead. Claude Code and MCP Inspector can send it as a header, which makes the server testable before any OAuth exists.
3. **Context comes from a curated overview plus scoped read tools,** not one big dump.
   - The server's `instructions` carry:
     - the glossary in `lib/copy.ts`;
     - the data model;
     - the rules, such as "Workload is derived, never stored".
   - `get_overview` returns today, this week and everything currently in flight in one call.
   - Each area then has its own `list_*`/`get_*` tools.
   - `read_collection` is a paginated, read-only escape hatch, so nothing in your data is out of reach.
   - Every result stays under claude.ai's limit of about 150,000 characters per tool result **[docs]**.
4. **Writes go through the same rules the app uses, not raw Firestore.**
   - All of today's write logic is client-side (`lib/firestore.ts`, written against the client SDK). It carries side effects that a naive server port would silently lose (§2.3).
   - Phase 0 therefore moves patch-building into pure shared builders used by **both** SDKs.
   - Every write tool then:
     - validates against the planner's invariants (sitting bounds, the locked layer, the slot id plus date);
     - bumps `updatedAt`, so open tabs hit their conflict guard;
     - logs itself to a per-user activity list you can review in Settings.
5. **Rollout in phases, smallest blast radius first.**
   1. Read-only first.
   2. Then additive writes: tasks, paper notes, checkpoints, goals and class logs.
   3. Then schedule edits, which need the calendar push and the template materialization.
   4. Deletes and settings come last, if at all.

## 1. Which Claude, and why a remote server

| Option | Works in | Auth | Effort | Verdict |
|---|---|---|---|---|
| **A. Remote server on Vercel (recommended)** | claude.ai web, Desktop, mobile, Cowork, Claude Code | OAuth for the hosted apps; a bearer header for Claude Code | Medium: the OAuth endpoints are most of it | ✅ One server for every Claude you use |
| B. Local stdio server on this Mac | Claude Desktop and Claude Code only, and only while this Mac is on | A service account in env, pinned to one uid | Low | Fallback only. No phone, no web. It also puts a god-mode service-account key on the laptop |
| C. Request-header auth only (no OAuth) | claude.ai only if your org has the beta | A static token | Low | Not available to a personal account today **[docs]**. Keep the token path for Claude Code |

**Decision D1** (§9) confirms option A.

Limits the hosted apps enforce **[docs]**:
- HTTPS on port 443 only.
- Requests come from `160.79.104.0/21`.
- A tool result can be about 150,000 characters.
- A tool call times out after 240 seconds.
- OAuth discovery, registration and token endpoints get 10 seconds to respond; refresh requests get 30 seconds.
- Resource subscriptions and sampling aren't supported, so don't build on them.
- Tools, resources and prompts **are** supported.

## 2. Current state: what the server has to work with

### 2.1 Data layout

- Everything lives under `users/{uid}/…` **[code]** `lib/firestore.ts:109-129`.
- **Collections under each user:**
  - `tasks`, `pomodoroSessions`, `days`, `dailySchedules`, `dayTemplates`, `weeklyReviews`
  - `terms`, `courses`, `topics`, `revisionItems`
  - `papers`, `paperGroups`, `files`, `aiInsights`
  - `goals`, `recurringTaskTemplates`
  - `meta/settings`
  - the Google Calendar connection and links
- **Subcollections:**
  - `courses/{id}/checkpoints` and `courses/{id}/classLogs`
  - `papers/{id}/notes` and `papers/{id}/annotations`
- The full-export list in `lib/export.ts:24-63` is the closest thing to an inventory. It omits `goals`, `recurringTaskTemplates`, `meta/settings`, annotations and the calendar documents, so the MCP inventory must be wider than the export.

### 2.2 Server-side pieces that already exist and can be reused

- **`lib/firebase-admin.ts`:** `adminDb()` and `adminAuth()`, with `ignoreUndefinedProperties: true` **[code]** `:33-54`.
- **`lib/admin-firestore.ts`:** `fetchInsightData(uid)`, an admin-SDK fetch of tasks, sessions, days, papers, courses, goals and terms.
- **`lib/admin-dailyloop.ts`:**
  - `fetchSettings`;
  - the private `dayFrame(settings)`, which builds the user's day in their timezone with `dayEndsAt` **[code]** `:17-36`;
  - due-revision counts and schedule fetches.
- **Pure domain logic (no Firebase imports) that runs unchanged on the server:**
  - `loadindex`, `next-action`, `gamify`, `tracking`, `weekplan`, `schedule`, `revision`, `courses`* and `dates`;
  - (\* `lib/courses.ts` imports the client SDK, so check what it needs before importing it on the server).
- **`lib/api-auth.ts`:** the role check (`disabled` is rejected) to copy for MCP callers **[code]** `:11-43`.
- **`lib/admin-dailyloop.ts` `writeDaySnapshot`** **[code]** `:96-…` already builds the Workload snapshot server-side from:
  - `fetchInsightData`;
  - the due and completed revision counts;
  - that day's `days` doc and schedule;
  - all passed to `buildLoadIndexSnapshot`.

  `get_overview` must extract and reuse that input assembly, not build a third version. (The client builds its own in `hooks/use-live-load-index.ts`.)
- **`lib/google-calendar-admin.ts`:** `runGoogleCalendarPush(uid)` **[code]** `:388` pushes FocusLab blocks to Google. `runGoogleCalendarSync` (`:551`, what `sync-now` calls) also pulls, which is heavier.
- **`lib/admin-audit.ts`:** `writeAuditEntry` is the **admin-action** log (`admin/auditLog`). Its `AuditAction` and `targetType` unions only cover admin targets **[code]** `types/index.ts:1152-1194`. It's the wrong place for a user's own edits (§5.3).

### 2.3 Why writes can't just be ported: client-side side effects

| Writer | Side effect a raw admin `update()` would lose |
|---|---|
| `updateTask` **[code]** `lib/firestore.ts:244-251` | Passing `completedAt: undefined` or `weeklyTargetDay: undefined` means "delete the field". With the admin SDK's `ignoreUndefinedProperties: true` it silently does **nothing** |
| `updatePaper` **[code]** `:683-706` | The same `undefined`→delete rule for seven fields (`readAt`, `fileId`, `weeklyTargetDay`, `queuedAt`, `shelvedUntil`, `droppedAt`, `inbox`), and for `anthropicFileId` and `layeredNotes` too. Changing `fileId` also clears `anthropicFileId` and `layeredNotes`. The status moves are built by the pure patch helpers in `lib/papers.ts`: `shelvePatch`, `dropPatch`, `restorePatch`, `queuePatch` and `unqueuePatch` (`:310-337`), and `startPassPatch` and `cancelPassPatch` (`:358-372`). They pass `undefined` to mean "clear" |
| `deleteCourse` **[code]** `:550-568` | Cascades to checkpoints, class logs and recurring templates, plus the open task instances those templates generated. Topics are kept |
| `deletePaper` **[code]** `:708-718` | Cascades to notes and annotations. Doesn't touch the Blob file, which needs `deletePaperFile` |
| `createPaper` **[code]** `:676-681` | Defaults `progress: 0` and `groupIds: []` |
| `incrementTaskCompletedPomodoros` | An atomic `increment`, never a read-then-write |
| `saveDailySchedule` **[code]** `:388-407` | Keeps `createdAt`. The caller picks `updatedAt`, which the two-tab guard reads |
| every writer | `trackWrite()`/`trackRead()` usage metering. It's a client module that debounces an `increment` into `users/{uid}/usage/{yyyy-MM}` as `{month, reads, writes}` (`lib/usage.ts:62-79`). The server can increment the same document |

### 2.4 Open tabs

- Every page reads through `onSnapshot`, so server writes appear live.
- `/plan/day` autosaves with a two-tab `updatedAt` guard **[code]** `hooks/use-day-autosave.ts:52-70`. If a tab sees a remote `updatedAt` it didn't write, it raises a conflict instead of overwriting.
- An MCP schedule write must therefore set a fresh `updatedAt`, never preserve the old one.
- The day timeline's undo stack is still unchecked. Could undoing after an MCP edit write the pre-edit slots back? Phase 4 checks this in the browser.
- The owner usually has their own FocusLab tab open, so this scenario is the normal case.

### 2.5 Things the server does **not** have

- **Firestore rules aren't in the repo** (there's no `firestore.rules`). The new top-level token collections (§4.4) must be readable only by the server. Before Phase 1 ships, check the deployed rules and add an explicit deny for them, or confirm the rules deny unknown collections by default.
- **The focus timer runs in the browser.** Its state is in localStorage (`focusos-active-session`), so the server can't start, pause or finish a sitting. Claude can read sessions but can't drive the timer.

## 3. Context design: how Claude gets "the whole context"

### 3.1 Server `instructions`

These are sent once at initialize, about 4–6k characters, and static, so they cache well:

- What FocusLab is and who it's for (a PhD scholar's workday OS).
- **The vocabulary:** the UI word next to the field name, generated from `lib/copy.ts` at build time so it can't drift. Examples:
  - "Workload" is the Load Index.
  - "Sitting" is a block.
  - "Skim / Read / Deep dive" are Pass 1 / 2 / 3.
- **The two day frames:**
  - `todayKey` is the logical day, which can run past midnight to `dayEndsAt`.
  - `scheduleDayKey` is the calendar date.
  - All dates are the user's timezone, never UTC.
- **Derived-never-stored values:**
  - Workload, catch-up hours, the on-track streak, the day score, "sessions left" and topics revised.
  - Claude reads them from `get_overview` and must never try to set them.
- **Planner rules:**
  - the locked layer (classes, routine and calendar blocks) is never moved;
  - sitting bounds are `minChunkMinutes` to `maxChunkMinutes`;
  - a block closes at 60% coverage;
  - dropped courses' work is never proposed.
- How to cite things back to the user (titles, not ids).

### 3.2 Tools (read): every one is `readOnlyHint: true`, so claude.ai can allow them without asking

| Tool | Returns | Built from |
|---|---|---|
| `get_overview({date?})` | The one-call snapshot: profile, timezone and day frame, enabled modules, sitting bounds; today's schedule with live block statuses; Workload snapshot and band; Up next; due-revision count; checkpoints in the next 14 days; the current term and active courses with weekly targets; papers in progress or queued; active goals with milestones; open tasks (counted, plus the top 15 by due date and priority); this week's plan summary; day-off status | `fetchInsightData`, `dayFrame`, `buildLoadIndexSnapshot`, `pickNextAction`, `scheduleSummary` |
| `list_tasks({status?, courseId?, bucket?, dueBefore?, cursor?})` / `get_task(id)` | Tasks | `tasks` |
| `get_day({date})` | The schedule with blocks and statuses, the `days` doc (session, review, brief, rollup, day off), and that day's focus sessions | `dailySchedules`, `days`, `pomodoroSessions` |
| `get_week({weekStart?})` | Seven days of blocks plus the week plan and the weekly review | `dailySchedules`, `weeklyReviews` |
| `list_courses({status?, termId?})` / `get_course(id)` | A course with its checkpoints, class logs, topics and coverage | `courses` plus subcollections, `topics` |
| `list_papers({status?, groupId?})` / `get_paper(id)` | A paper with its pass state, notes, annotations and layered summary (not the PDF bytes; see D6) | `papers` plus subcollections |
| `list_goals()` / `list_terms()` / `list_paper_groups()` | Those collections | |
| `get_revision_queue({date?})` | Revision cards due | `revisionItems` |
| `get_focus_history({from, to})` | Sessions plus per-day totals | `pomodoroSessions`, `lib/analytics.ts` |
| `search({query, kinds?})` | A title and text match across tasks, papers, notes, courses and goals | Done in memory after a scoped fetch. One user's data is small |
| `read_collection({name, cursor?, limit?})` | The escape hatch: raw documents from an **allowlisted** collection, paginated, with a size cap | All collections in §2.1 except token and calendar-secret documents |

Every list tool:
- paginates with an opaque cursor;
- trims each result to about 120k characters;
- says when it trimmed ("12 more, pass cursor").

### 3.3 Resources and prompts (Phase 5, optional)

- **Resources:** `focuslab://glossary` and `focuslab://data-model`, which are the same text as the instructions, browsable. Later, a paper's PDF as a binary resource (D6).
- **Prompts:** "Plan my week", "Review today" and "What should I read next?". These are thin wrappers that tell Claude which tools to call.

## 4. Auth design

### 4.1 Phase 1: personal access tokens (for Claude Code and MCP Inspector)

1. **Create the token.**
   - `/settings` → "Connected apps" → **Create token** → choose a label and a scope (`read`, or `read write`).
   - The server returns `fl_pat_<32 random bytes, base64url>` and shows it once.
   - It stores **only the sha256** in `mcpTokens/{hash}` as `{uid, kind: "pat", scopes, label, createdAt, lastUsedAt, revokedAt?}`.
2. **Connect Claude Code.** Run:

   ```
   claude mcp add --transport http focuslab https://<domain>/api/mcp --header "Authorization: Bearer fl_pat_…"
   ```

3. **Revoke.** The token can be revoked from the same card.

### 4.2 Phase 2: OAuth 2.1 (for claude.ai, Desktop and mobile)

The endpoints, all on the FocusLab origin:

| Endpoint | Does |
|---|---|
| `401` from `/api/mcp` | `WWW-Authenticate: Bearer resource_metadata="https://<domain>/.well-known/oauth-protected-resource", scope="read write"`. Claude requires the `401` and ignores the header on a `200` **[docs]** |
| `GET /.well-known/oauth-protected-resource` (also at `/.well-known/oauth-protected-resource/api/mcp`) | `{resource: "https://<domain>/api/mcp", authorization_servers: ["https://<domain>"], scopes_supported: ["read","write","offline_access"]}`. **`resource` must equal the URL exactly as typed into Claude** **[docs]** |
| `GET /.well-known/oauth-authorization-server` | `issuer`; the authorize, token, registration and revocation endpoints; `code_challenge_methods_supported: ["S256"]`; `token_endpoint_auth_methods_supported: ["none"]`; `client_id_metadata_document_supported: true`; `grant_types_supported: ["authorization_code","refresh_token"]` |
| `POST /api/oauth/register` (DCR, JSON) | Registers a public client. Accepts only `https://claude.ai/api/mcp/auth_callback` and loopback redirects (`http://localhost/*` and `http://127.0.0.1/*`, matched without the port, for Claude Code **[docs]**) |
| CIMD | A URL-shaped `client_id` is fetched with an SSRF guard: HTTPS only, a host allowlist, 5s timeout, 10KB cap, cached. Its `redirect_uris` must contain the requested one. **The URL claude.ai's hosted apps use for their published identity isn't confirmed.** Claude Code's is `https://claude.ai/oauth/claude-code-client-metadata` **[docs]**; the hosted apps' may be on another host. If Claude picks CIMD and the host fails the allowlist, the flow **fails instead of falling back to DCR**. So in Phase 2, log every incoming `client_id` on the first real connection, then set the allowlist to what was seen. Until then, accept any HTTPS host and keep the SSRF guard |
| `GET /oauth/authorize` (a page) | Shows the consent screen. The sign-in step (below the table) comes first. The consent card shows the client name, **the redirect hostname** and the scopes as checkboxes ("See your FocusLab data" / "Make changes"). On Allow, it posts with the Firebase ID token to `/api/oauth/authorize/approve` |
| `POST /api/oauth/authorize/approve` | Checks the ID token (`verifyActiveUser`), then issues a code: 60s TTL, single use, stored hashed with the PKCE challenge, redirect URI, resource and scopes. Redirects back with `code` and `state` |
| `POST /api/oauth/token` (**form-urlencoded**) | Handles `authorization_code` (with the S256 verifier, the redirect URI and the resource checked) and `refresh_token`. The refresh token **rotates on every use**, and the old one dies. Errors are RFC 6749 codes; an expired or used refresh token gets `invalid_grant` **[docs]** |
| `POST /api/oauth/revoke` | RFC 7009 revocation |

**The sign-in step: a gap that exists today.**
- If you aren't already signed in, `/login` has **no return-to support**. Signed-out visitors are bounced to `/login`, and a signed-in visit to `/login` goes to `/dashboard` (README, Authentication). The `/oauth/authorize?...` parameters would be lost and the flow would die.
- **Fix:** `/oauth/authorize` stores its full query in `sessionStorage` before sending you to `/login?returnTo=/oauth/authorize`. `/login` (or `AuthProvider`'s redirect) honours `returnTo` for same-origin paths only, and the page restores the query after sign-in.
- **Mobile:** when you connect from the Claude phone app, the flow runs in an in-app or system browser, where Google's `signInWithPopup` (`components/auth-provider.tsx:121`) often fails or is blocked.
  - The consent page should offer email/password and email-link sign-in (both already exist) beside Google.
  - Use `signInWithRedirect` for Google on this page, not the popup.
  - Acceptance criterion 15 tests this.

**Token format:**
- Tokens are opaque random strings, looked up by hash. A JWT would save one Firestore read per call, but an opaque token can be revoked instantly and one read is cheap.
- Access tokens last 1 hour and refresh tokens 60 days (**D5**).
- Each token records its `resource`. A token issued for any other audience is rejected (MCP spec: "MUST validate audience").

### 4.3 On every MCP request

1. Hash the bearer, look up `mcpTokens`, and reject anything missing, revoked or expired with a `401`.
2. Load the user's role and reject `disabled`. Cache the role for 60 seconds per warm instance. This mirrors `verifyActiveUser` **[code]** `lib/api-auth.ts:33-43`.
3. Check the kill switch, and the per-user gate (**D2**). The kill switch is a **new** `AdminSettings.mcpEnabled` field, which needs a toggle in the admin panel's settings next to `aiGloballyEnabled`.
4. Pass `uid` and `scopes` into the tool context. **Every query is built from `ctx.uid`.** No tool takes a uid argument. Because the Admin SDK bypasses Firestore rules, this is the only thing keeping users apart.
5. A write tool called with a token lacking the `write` scope gets a `403` with `error="insufficient_scope"`, and Claude steps up.
6. Update `lastUsedAt`, debounced to once every 10 minutes.

### 4.4 New collections

- **`mcpTokens/{sha256}`:** PATs, access tokens and refresh tokens, each with `{uid, kind, clientId, scopes, resource, expiresAt, revokedAt?, familyId}`. When a refresh token is reused after rotation, the whole `familyId` is revoked.
- **`oauthClients/{clientId}`:** DCR clients.
- **`oauthCodes/{sha256}`:** codes with a TTL. Set a Firestore TTL policy on `expiresAt`.

One more, per user: `users/{uid}/mcpActivity`, the write log from §5.3. The client may read it but never write it.

The first three are top-level so the token lookup is one `get`. They are never readable by clients (§2.5). `lib/admin-user-delete.ts` must delete a user's tokens and clients when the account is deleted.

## 5. Write design

### 5.1 Phase 0: one set of write rules for both SDKs

1. **Create `lib/patches.ts`** (pure, no Firebase import). It holds builders such as `taskPatch(patch, DELETE)` and `paperPatch(patch, DELETE)`.
   - Each returns the payload with the clear-field and cascade-invalidation rules from §2.3.
   - `DELETE` is the SDK's sentinel: `deleteField()` on the client, `FieldValue.delete()` on the admin side.
2. **Make `lib/firestore.ts` call them,** so the client behaves exactly as it does now. Then add `lib/admin-writes.ts`, which calls the same builders for the server.
3. **Port the cascades** for course and paper deletion to `lib/admin-writes.ts` in the same shape, even though the deletes ship last.
4. **Add a pure verify script, `scripts/verify-patches.ts`.** For each builder it asserts the clear-field rules: `undefined` becomes the sentinel, and `fileId` clears `anthropicFileId` and `layeredNotes`.
5. **Export `dayFrame` from `lib/admin-dailyloop.ts`,** so MCP tools and the crons agree on which day it is.

### 5.2 Write tools, by phase

Annotations:
- additive tools are `readOnlyHint: false, destructiveHint: false`;
- the Phase 6 deletes are `destructiveHint: true`;
- every write takes `idempotencyKey?`.

**Phase 3 (additive, low risk):**

| Tool | Notes |
|---|---|
| `create_task` / `update_task` | Same fields as the UI. `courseId` must be an **active** course. `bucket` only with `courseId`. `maxChunkMinutes` is clamped to the user's `[minChunkMinutes, maxChunkMinutes]`. `fixedTime` implies `splittable: false` |
| `complete_task` / `reopen_task` | Mirrors the UI: it sets `completedAt` and `previousStatus`, and reopening restores `previousStatus` (`types/index.ts:171`) |
| `create_paper` (into the inbox) / `update_paper_status` | Status changes go through the exit patches in `lib/papers.ts`, never raw fields |
| `add_paper_note` | Notes only. Annotations need PDF coordinates (`HighlightQuad`), so none in v1 |
| `create_checkpoint` / `update_checkpoint` | Under the course. Status uses the `CheckpointStatus` set |
| `log_class` | `saveClassLog`, keyed by date, merge |
| `create_goal` / `update_goal` / `update_milestone` | |
| `set_day_off` / `clear_day_off` | Only the current or a future logical day |

**Phase 4 (the schedule: needs the most care):**

| Tool | Notes |
|---|---|
| `add_block({date, title, type, startTime, endTime, taskIds?, courseId?, bucket?})` | The rules are below this table |
| `move_block({date, slotId, startTime, endTime})` / `remove_block({date, slotId})` | Address by **date + slotId**, because recurring class and routine slots reuse ids on every date. Refuse `isLockedSlot` and `isFixedSlot` blocks. Refuse blocks that have started or finished (the coverage history depends on them) |

The rules for `add_block`:
- **Day with no saved schedule.** If the date has no saved `dailySchedules` document, build it first the way `/plan/day` does:
  - start from the default template (`scheduleFromTemplate`);
  - add the class and routine blocks with `mergeMissingLockedSlots`;
  - otherwise the first MCP write would create a day missing its classes.
- **Validation.** `validateSlots` must pass. A sitting outside `[min, max]ChunkMinutes` is refused, with a hint to split it.
- **`plannedMinutes`.** It is set to the duration, since it feeds `plannedMinutesThisWeek`.
- **Writing.** A fresh `updatedAt`, then `runGoogleCalendarPush(uid)` when the integration is connected. This is the push-only half; `sync-now`'s full sync also pulls, which isn't needed here. The push is best-effort, like the autosave's: a failed push doesn't fail the write, and it says so in the result.

Week planning (`/plan/week`'s propose, accept and replan) stays **in the app**. That flow is the largest chunk of client-only logic, and the planner's user decisions are its point. Claude can read the week and add or move individual sittings; it doesn't run the planner.

**Phase 6 (only if wanted, D3):**
- `delete_task` (no cascade);
- `delete_course` and `delete_paper` through the cascades ported in Phase 0, and paper deletion also removes the Blob file;
- `grade_revision` (the spaced-repetition update from `lib/revision.ts`);
- a narrow `update_settings` (for example `maxChunkMinutes` only).

### 5.3 Every write also

- **Activity log.** It appends `{at, clientId, clientName, tool, targetType, targetId, before, after}` to a **new per-user** collection, `users/{uid}/mcpActivity`. The "Connected apps" card shows the last 50 entries, so you can see exactly what Claude changed. The admin `auditLog` is not used: it's typed for admin targets (§2.2), and these are the user's own edits.
- **Usage.** It increments `users/{uid}/usage/{yyyy-MM}` (`reads`, `writes`) through the Admin SDK `FieldValue.increment`, the same document the client meter flushes to (§2.3), so MCP traffic is counted.
- **Result.** It returns the document after the write, so Claude can say what changed.
- **Closed days.** It never writes to a closed day. A day is closed when its `days` doc has `closedAt` or `session.endedAt`, the same test `closeFinishedDays` uses **[code]** `lib/admin-dailyloop.ts:154-156`. It also never writes to any date before the logical today. Past days are read-only through MCP.

## 10. Acceptance criteria

1. **Overview.** In claude.ai, after adding the connector and approving it on the FocusLab consent screen, "what's on my plate today?" answers from `get_overview`. It shows the same blocks, Workload band and Up next as `/dashboard` at that moment, checked side by side in Chrome. Workload comes from the input assembly extracted from `writeDaySnapshot` (§2.2). If the client's live number and the server's differ, that's a finding to explain, not to paper over.
2. **Day frames.** The overview's "today" (logical day) and schedule date stay apart the way the app's do. Test this in daytime by temporarily raising `LATEST_DAY_END_MINUTES` and setting a late `dayEndsAt` on the test account. That is the standing testing tip; set it back to Midnight before reverting the constant.
3. **Isolation.** A token for user A can't read or write anything of user B's. No tool accepts a uid. Tested with tokens for the test account and for a second throwaway account: a guest/anonymous or email sign-up made for this, deleted afterwards.
4. **Read-only tokens.** Write tools refuse a `read`-only token with a `403`, `insufficient_scope`.
5. **Clearing fields.** An MCP `update_task` that clears `weeklyTargetDay` really deletes the field, verified in the export. The same goes for `update_paper` with `fileId`, which also clears `layeredNotes`.
6. **Locked blocks.** An MCP `move_block` on a class or routine block is refused with a plain message.
7. **Sitting bounds.** An MCP `add_block` longer than `maxChunkMinutes` is refused.
8. **First write to an empty day.** On a day never opened, an MCP `add_block` produces a day that still has its classes and routine blocks.
9. **Open tabs.** With `/plan/day` open in another tab, an MCP schedule write appears live, and the tab's next autosave shows the conflict instead of overwriting.
10. **Calendar.** With Google Calendar connected, an MCP-added block appears in Google Calendar.
11. **Revocation.** Revoking in Settings makes the next Claude call fail with a `401`, and Claude asks to reconnect.
12. **Refresh rotation.** Reusing an old refresh token revokes its whole family.
13. **Result sizes.** No tool result exceeds 150,000 characters on the real account's data. Measure the largest: `read_collection` on `pomodoroSessions`.
14. **Activity.** Every MCP write appears in the "Connected apps" activity list with the tool, the target, and before and after.
15. **Mobile, signed out.** Connecting from the Claude phone app while signed out of FocusLab in that browser reaches the consent screen after sign-in, with the OAuth parameters intact, and completes.

## 11. How it gets verified

- **Local first (Phase 1).**
  - Run `pnpm dev`, create a PAT on **the test account (suyashbima@)** and connect `npx @modelcontextprotocol/inspector` to `http://localhost:3000/api/mcp`.
  - Then add it to Claude Code with `claude mcp add --transport http … --header`.
  - Dev talks to the **production** Firebase project, so every write test uses the test account only.
- **In the app.** Each write is confirmed by watching the change land in the running app in Chrome on the test account, not by reading Firestore alone.
- **claude.ai (Phase 2) needs a public HTTPS URL** on port 443. Two ways to get one:
  - deploy to production (the feature sits behind the kill switch until verified);
  - or tunnel localhost temporarily, for example with `cloudflared`. Use the tunnel URL as both `resource` and issuer, or `resource` won't match **[docs]**.
- **Things never done while testing:**
  - hitting `close-day`, `daily-insight` or the rollup routes: they act on every user, and the rollup spends AI money;
  - reusing a token from the owner's real account.
- **Owner's open tab.** The owner usually has a FocusLab tab open, which joins live sync. Check the open-tab conflict (criterion 9) with the test account's own two tabs, inside the MCP tab group.
