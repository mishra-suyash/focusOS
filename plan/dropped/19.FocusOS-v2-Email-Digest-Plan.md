## 0. TL;DR

The spec's architecture (a pull queue, with the Mac mini making outbound requests only) fits this app and is kept. The main changes from the spec:

1. **Firestore, not SQL.** The four tables become top-level, Admin-SDK-only collections. Claiming and creating runs use a transaction on one state document.
2. **A separate Google Cloud project for Gmail.** The existing OAuth client is in the same project as Firebase sign-in, so the Gmail consent settings would be shared with every user's login and Calendar.
3. **Locked to one account by an env var.** The app has open sign-up and guests, and the worker runs on one personal Claude subscription.
4. **The export is limited by Gmail quota, not by concurrency.** Eight parallel fetches would hit Gmail's per-user limit on a large mailbox. The export needs a per-account budget and a cheaper fetch for promotions and social.
5. **Three gaps in the spec would lose mail or hide actions** (§3, D1–D3). Each needs a decision.

**Estimate:** about 42 focused hours (§13). Owner time is extra: Google Cloud setup, consent clicks and env vars.

## 3. Decisions needed before I start

Each has a recommendation. "Go with your recommendations" is a complete answer.

**D1. What does "Today's mail" show after a second run?** The spec shows the *latest* succeeded run, and each window starts where the last one ended. So a 14:00 "Run now" covers 07:44–14:00 only, and **the morning's unfinished actions vanish from the dashboard**.
→ *Recommended:* verdict, time and noise counts from the latest run; action, suspicious and FYI items **merged from every succeeded run today**, deduplicated by (account, message), newest wins.

**D2. Windows per account, or one per run?** With one global window, a mailbox that fails at 07:43 while the others succeed is skipped for good: the next window starts after the gap.
→ *Recommended:* each account keeps its own `covered_until`, advanced only when a run containing it **succeeds**. Same 36 h cap and 24 h first-run rule. The run still stores overall `window_start`/`window_end` as specified.

**D3. More than 300 messages.** Once the window advances, messages past the cap are never analysed.
→ *Recommended:* keep the cap. Choose fairly: personal and updates mail before promotions and social, newest first, round-robin across accounts. Save `truncated` and the skipped count on the run, and show "212 messages not read" on the card and in history.

**D4. Missed or expired scheduled run.** If the Mac is off from 07:43 to 09:43, the run expires, and there's no digest until tomorrow or "Run now".
→ *Recommended:* build as specified, plus one small backstop: the first worker claim after 07:43 IST creates today's scheduled run if there isn't one yet, **or if it expired without ever being claimed**. The replacement's ID ends in `_retry`, so it happens at most once a day. This also starts the run within a minute of 07:43, whatever time Hobby's cron fires. A run that was claimed and then expired isn't recreated, because that is a worker fault to look at. Say no to keep cron only.

**D5. Unknown message IDs: drop the item, or reject the whole result?** "Reject any item" reads per item.
→ *Recommended:* drop the item, store the count, return `rejected: [{ index, reason }]`, show "1 item rejected" in history. A malformed body or wrong `run_id` still fails the whole post with 422.

**D6. Publishing status for the new Google project.** Testing status is unusable for a daily job (§9). *Personal mode* (one Google account, the one that created the project) can't serve several mailboxes.
→ *Recommended:* External, **In production, unverified**. You click past a warning once per account.

**D7. The test tool.** Claim atomicity can't be tested honestly without Firestore.
→ *Recommended:* the Firestore emulator, in CI and locally. Local needs `brew install openjdk@21`.

## 4. Data model

All collections are top-level and reachable only through the Admin SDK. Field names are camelCase, the repo's convention.

### 4.1 Collections

**`emailAccounts/{accountId}`** — `accountId` = first 32 hex chars of sha256(`uid|googleSub`), so reconnecting updates in place even if the address changes.
`uid, email (lower-cased), googleSub, label, scopes[], status (active | needs_reconnect | revoked), lastError?, createdAt, lastExportedAt?, coveredUntil?`

**`emailAccountTokens/{accountId}`** — `uid, ciphertext, keyVersion, updatedAt`. Separate from the account so listing accounts never loads a token.

**`emailDigestState/{uid}`** — `activeRunId?, lastSucceededRunId?, lastScheduledDate?` (so an idle claim needn't query for today's run). The single document every transition goes through.

**`emailDigestRuns/{runId}`** — ID is `{uid}_schedule_{yyyy-MM-dd}` for scheduled runs (plus `_retry`, D4), auto otherwise.
`uid, trigger (schedule | manual), status (pending | claimed | succeeded | failed | expired), requestedAt, claimedAt?, completedAt?, durationMs?, localDate, windowStart?, windowEnd?, accountsIncluded[] ({ accountId, email, windowStart, messageCount, skippedCount, gapHours?, error? }), messageCount, skippedCount, truncated, actionCount, rejectedItemCount, verdict?, summaryMarkdown?, noiseCounts?, stats?, error?, workerId?, exportStartedAt?, exportCompletedAt?, exportDurationMs?, resultHash?`

**`emailDigestRuns/{runId}/private/export`** — `messages: string[]` of `accountId/messageId/threadId` (the spec's `exported_message_ids`, §7.4). About 20 KB at 300.
**`emailDigestRuns/{runId}/private/result`** — `json` (the validated result, unknown keys removed).

**`emailDigestItems/{itemId}`** — `itemId` = first 32 hex chars of sha256(`runId|accountId|messageId`).
`uid, runId, localDate, bucket, accountId, accountEmail, gmailMessageId, gmailThreadId, sender, subject, actionText?, deadline?, deadlineText?, priority (1–5), reason?, gmailUrl, done, doneAt?, createdAt`

**`emailDigestDone/{doneId}`** — sha256(`uid|accountId|messageId`). Present means done. Carry-forward is then a `tx.getAll` of known IDs, with no cross-run query. Ticking writes the item and this marker in one transaction, and unticking deletes the marker.

### 4.2 Indexes

Only one composite: `emailDigestRuns` (`uid` asc, `localDate` desc, `requestedAt` desc). Claim reads the state document. Items are read by `runId`, or `uid` + `localDate`, both equality-only, which Firestore serves from its automatic indexes. The spec's (account_email, gmail_message_id) index is replaced by `emailDigestDone`.

### 4.3 Access control

- **Why an env var and not `role === "owner"`:** the test account used for checking changes isn't the owner, and the owner role can't be reassigned **[code]** `lib/admin-roles.ts`. The role check also wouldn't separate dev from production (C5).
- **UI visibility:** a new setting, `UserSettings.emailDigestEnabled?: boolean`, default off. It's cosmetic; the server enforces access.
- **Why not a module in `lib/features.ts`:** (a) an `optIn` module appears on everyone's Features page; (b) `withModuleToggled` freezes the pack into an explicit list **[code]** `lib/features.ts:133`, so the owner would stop receiving new modules; (c) a nav item with a module everyone else has off would add "+1 more module available" for every user, pointing at a toggle that isn't there **[code]** `components/app-shell.tsx:208`.
- **Precondition, owner:** confirm the live Firestore rules have no match for the six `email*` collections (default deny), or add `allow read, write: if false`. I'll verify with a client-SDK read that must be refused. Not a formality, because the rules aren't in the repo.

## 5. Run lifecycle

`pending → claimed → succeeded | failed | expired`

Each transition is one Firestore transaction that reads `emailDigestState/{uid}` first. Server transactions are serializable, so two concurrent ones can't both succeed on the same prior state.

| Operation | Transaction |
|---|---|
| **Create** | Read state and its active run. If it's stale, expire it; if still live, return it with `created: false`. A scheduled run whose ID already exists returns that run. Otherwise create it and set `activeRunId`. |
| **Claim** | Read state and active run. Expire if stale. If `pending`, set `claimed`, `claimedAt`, `workerId`. Otherwise 204. At most one run per uid is ever live, so "oldest pending" is that run. |
| **Result / fail** | Read the run. Write the outcome and clear `activeRunId`. |
| **Expire** | `pending` for 2 h since `requestedAt`, or `claimed` for 2 h since `claimedAt`. Checked by the cron, by create and claim, and by every user read of the active run. |

Edge cases:

- **Longest life of a run.** Each state gets its own 2 h, so a run claimed at 1 h 59 min can live almost 4 h in total. Counting both from `requestedAt` would kill a run minutes after a Mac that has just woken up claimed it.
- **Late result** for an `expired` run → 409. `failed` → 409.
- **Worker crash after claiming.** "Run now" returns the stuck run until it expires. The contract tells the worker to persist its run ID and call `/fail` on restart.
- **`localDate`** comes from `requestedAt`, so a run requested at 23:59 belongs to that day.
- **No connected accounts:** the cron creates nothing and records why. "Run now" returns 409 "Connect a Gmail account first".
- **`cronEnabled` off** skips the scheduled run and D4's backstop. "Run now" still works. `aiGloballyEnabled` doesn't apply; no AI runs here.

## 7. Export and result

### 7.1 Window

`start = coveredUntil ? max(coveredUntil, now − 36 h) : now − 24 h`, per account (D2). `end = now`. When the 36 h cap bites, `gapHours` is saved and shown.

**Boundary:** a message can reach Gmail just before `end` but not be searchable yet, and the next window would then skip it. So listing starts 2 minutes before `start`, and messages already exported by the previous succeeded run are removed by ID.

**Frozen on first export.** Window and chosen IDs are saved *before* streaming. A retry exports the same list, so a result built on either copy validates. `exportCompletedAt` is written before the stream closes, so a worker can't hold a complete zip the server doesn't know about. A result without `exportCompletedAt` gets 409.

### 7.2 Listing

Two queries per account (5 units a page), each with `after:<unix seconds>`:
- **Body set:** `in:inbox -category:promotions -category:social`
- **Metadata set:** `in:inbox {category:promotions category:social}`

Knowing the category from the query avoids paying for a full fetch to find out. `in:inbox` excludes spam and trash.

### 7.3 Fetching within quota

Google's page gives 6,000 units per minute per user, 20 units for `messages.get`, and 60 for `format=full`. These figures came through a page summary and not verbatim rows, so **Phase 0 re-checks them in the new project's Quotas page**.

| | Units each | Per minute, one mailbox |
|---|---|---|
| Body set, `format=full` | 60 | 100 |
| Metadata set, `format=metadata` | 20 | 300 |

- **Per-account limiter:** a sliding 60-second window capped at 5,400 units (90% of the limit). Not a burst-plus-refill bucket: one with a large burst spends nearly double the limit in its first minute and causes the 403s it exists to prevent. Accounts don't share a limit.
- **Global concurrency 8**, shared by all accounts.
- **Backoff** on 403 rate-limit errors and 429: exponential with jitter, four tries.
- **Estimates, not measurements:** a normal day (about 40 full messages over several accounts) fits in the first window, under 15 s. Worst case, 300 full messages in one mailbox, is 18,000 units: three full windows of 5,400, then the remaining 1,800, so about 185 s of waiting and **190–200 s in all**. A slow near-cap run can hit the 240 s stop and truncate (D3).
- **Deadline:** at 240 s stop fetching, write the manifest with `truncated: true`, and close the zip. Unfetched IDs are then removed from the frozen list, so items can't cite mail the worker never received. **That trim happens only until the first completed export.** A retry right after a large export starts already throttled (Google counts 4xx responses too) and may carry fewer messages, but it never shrinks the saved list, so items based on the first copy still validate.
- **Duration** is stored as `exportDurationMs` on each run. I'll report real numbers for a normal and a near-cap run; I can't before it's built.

One deviation: `format=metadata` has no MIME parts, so promotions and social messages carry `attachments: []` and `attachments_omitted: true`.

### 7.4 Zip

- **`fflate`** streaming zip, already in the lockfile through jsPDF, promoted to a direct dependency. Streamed responses are exempt from Vercel's 4.5 MB limit.
- **Manifest last,** because it carries final counts. Extra fields: per-account `window_start`, `skipped_count`, `gap_hours`.
- **After the first byte the status is already 200,** so a mid-stream failure gives a broken zip. The contract tells the worker to check that the archive opens and contains `manifest.json`. Run, account and listing checks happen before streaming and return real errors.
- **Paths** are built from the stored account email and IDs matching `^[0-9a-f]+$`, never from message content.
- **Body text:** prefer `text/plain`; otherwise `html-to-text` with images, styles, `blockquote` and `.gmail_quote` skipped. Then strip zero-width and bidi control characters, then quoted replies (`>` runs, "On … wrote:", Outlook headers), then cut at 8,000 characters without splitting a surrogate pair.
- **One bad message doesn't fail the run.** It's counted in the manifest. One bad account is reported and the others continue. `invalid_grant` sets `needs_reconnect`; network and rate errors leave the status alone.
- **If every account fails,** the run is marked `failed` and the export returns 502, so the worker doesn't analyse nothing.

### 7.5 Result

1. Token check, then a byte-counted body read capped at 1,000,000 bytes. `Content-Length` isn't trusted.
2. zod, strict limits: at most 300 items, `verdict` 200 characters, `summary_markdown` 6,000, `sender` 320, `subject` 500, other text 1,000. `schema_version` must be 1 and `run_id` must match the path.
3. Match each item on **(account, message ID)**, not message ID alone: Gmail IDs are per mailbox, so a bare ID could be attached to the wrong account. Unmatched or duplicate items are dropped and counted (D5). `gmail_thread_id` is replaced with the exported one.
4. `gmailUrl` is built here: `https://mail.google.com/mail/?authuser=<encoded email>#all/<messageId>`. No URL field is accepted. Phase 5 clicks it with several signed-in accounts, because I haven't verified this form.
5. One transaction: run, up to 300 items, `private/result`, state, and `coveredUntil` on the successful accounts. Done markers are read in it, so carry-forward can't race a tick. That's under 350 writes.
6. **Idempotent:** same body hash on a succeeded run → 200 `{ already: true }`, nothing written. A different body → 409.

`docs/email-digest-result.schema.json` is generated from zod with `z.toJSONSchema()` by `pnpm email-digest:schema`. CI fails if the file is out of date.

## 8. Security

| Concern | Measure |
|---|---|
| Worker token | Compare SHA-256 digests with `timingSafeEqual`. An unset or under-32-character `DIGEST_WORKER_TOKEN` means every worker route returns 503. Only the four worker routes read it. |
| Refresh tokens | AES-256-GCM, random 12-byte IV, AAD `uid|accountId` (a ciphertext can't be moved to another account), stored with `keyVersion`. `EMAIL_TOKEN_KEY` is 32 bytes base64, checked on use. Losing it means reconnecting every account. |
| OAuth state | HMAC with a `purpose: "gmail"` field, nonce and 10-minute expiry, **plus** an HttpOnly `SameSite=Lax` cookie holding the nonce. The Calendar state has neither purpose nor browser binding **[code]** `lib/google-calendar-admin.ts:71`, so it isn't reused. |
| Scopes | Exactly `openid email gmail.readonly`, without `include_granted_scopes`. Google lets a user untick scopes, so the callback checks what was granted: missing `gmail.readonly`, or anything broader, is revoked and refused. |
| Stored email | No bodies, snippets or attachments. Runs and items hold sender, subject and the worker's text. |
| Prompt injection | Results can be wrong in *content* even with every check passing. Limits: cited messages must be exported, URLs are ours, and no field can act. **Residual risk:** sender and subject are the worker's copy, so a manipulated item could mislabel a real message. The link always opens the real one. |
| Rendering | React text nodes everywhere. `summary_markdown` uses `react-markdown` with `skipHtml`, then `rehype-sanitize`, with an allow-list **without `a` or `img`**. A link in a model-written summary of untrusted mail is a phishing path, and a remote image leaks that it was opened. |
| Logging | Run ID, status, counts, durations. Google errors are mapped to a fixed set of messages before storing, since raw errors can quote request content. `/fail` text is escaped and shown only to the owner. |
| CSRF | User routes need a bearer ID token, which a cross-site form can't send. |
| Dependencies | Three additions: `html-to-text`, `react-markdown`, `rehype-sanitize`, plus `fflate` promoted. Pin versions older than two weeks. Quoted-reply stripping is hand-written. |

## 9. Google Cloud setup (for `docs/email-digest.md`)

1. Create a **new project**, separate from Firebase. Enable the Gmail API.
2. Consent screen: External. Scopes `openid`, `email`, `gmail.readonly` (a *restricted* scope).
3. OAuth client, Web application. Redirect URIs: `https://<domain>/api/email-digest/accounts/callback` and the `http://localhost:3000` equivalent. Locally, `GMAIL_OAUTH_REDIRECT_URI` must be the localhost one, or the state cookie won't arrive.
4. Choose a publishing status:

| Option | Refresh tokens | Accounts | Verdict |
|---|---|---|---|
| **Testing** | **Expire after 7 days.** Every account needs reconnecting weekly. | Up to 100 listed test users | Not usable for a daily job. Fine for the first test. |
| **In production, unverified** | No 7-day expiry | 100 new users over the project's lifetime; a warning screen each time you connect | **Recommended.** Google's help page lets limited-audience apps continue without verification. |
| **Personal mode** | No 7-day expiry, no warning | **Only the account that created the project.** Chosen at setup, permanent | Works for one mailbox only. |
| **Internal** | No 7-day expiry | Only one Workspace organisation | Only if you administer that Workspace. |
| **Verified** | No 7-day expiry | Unlimited | Restricted-scope review. Not worth it for personal use. |

**Moving from Testing to In production doesn't rescue tokens already issued.** Reconnect each account afterwards.

Other ways a token stops working, all shown as "Reconnect": you change that account's password (Google names Gmail scopes specifically), you remove the app's access, it goes unused for six months, or an admin restricts the service.

**Institute Google Workspace accounts may block unverified third-party apps.** The error is usually `admin_policy_enforced` or "access blocked", and only the Workspace admin can allow the app. The settings page says so plainly and doesn't offer a pointless retry. **Try the institute account first in Phase 0**, before any code depends on it.

Google's quota page also says *AI agents* calling Workspace data must use MCP servers from 2027-02-01 or stay on Standard Tier limits. This export runs within Standard Tier figures. Re-check the page in January.

## 10. UI

**Dashboard card, "Today's mail"** (`components/email-digest-card.tsx`): full width, directly below `NextActionCard`, rendered only when `emailDigestEnabled`. Not a Customize widget, and not a module, so there's no second flag to drift (`13` C1).

- Header: verdict, `Updated 07:44 IST · scheduled` (or `· manual`), Run now. Times use `Intl.DateTimeFormat` with `Asia/Kolkata`, whatever the browser's zone.
- **Action** items by deadline (none last), then priority (1 = highest), then subject. Each has a done checkbox, account badge, deadline and "Open in Gmail" (`target="_blank" rel="noopener noreferrer"`). Overdue deadlines are marked.
- **Suspicious** in the red alert style, text only, above the fold. "Open in Gmail" stays; nothing else is clickable.
- **FYI** collapsed. **Noise** as counts.
- Notes when true: messages skipped, coverage gap, a failed account.
- No success today: the most recent one, with its date. Never run: what to do next.
- **Run now:** optimistic disable, then "Waiting for Mac mini…" (pending) or "Reading your mail…" (claimed). Polls `/today` every 10 s only while a run is live and the tab is visible. Stops on completion, expiry, error or unmount, with a message for each.
- A failed tick reverts and says so.

**Reconnect banner** above `AlertsBanner`, listing the accounts. It isn't stored in `alerts`: that collection is client-writable and deduplicated per day, so a fixed account would keep its alert.

**Settings:** a card on `/settings` (owner only, through `/access`) with the on/off switch and a link to **`/settings/email-digest`**: accounts with label, status, last export and error; Connect another Gmail account; Reconnect; Disconnect with inline confirmation (no `window.confirm`). Disconnect revokes at Google, deletes the token, and keeps the account record as `revoked` so history keeps its labels. If Google can't be reached, the local token is still deleted and the page links to Google's permissions page.

**History `/email-digest`:** nav entry in "More", shown only when enabled. Runs grouped by IST date, 20 per page, "Load older". Each row has time, trigger, status, messages, actions and error, and expands to the same digest component the card uses. Not-allowed users see the normal not-found page. Every screen is checked at phone width and in dark mode.

## 12. Tests

**`pnpm verify:email-digest`** (pure, every CI run): window calculation (first run, normal, 36 h cap, per account, after a failure); IST grouping on both sides of 18:30 UTC, and that `dayEndsAt` doesn't affect it; selection fairness at the cap; the limiter never exceeds 5,400 units in any 60 s window; text extraction (HTML, quoted replies, Unicode cut, zero-width characters); result schema limits; item matching, including a valid ID under the wrong account; Gmail URL encoding; token encryption (round trip, wrong AAD, tampering, wrong key); state signing (expiry, wrong purpose); worker token check; schema-file drift; the LLM import ban.

**`pnpm verify:email-digest-store`** (Firestore emulator): **two concurrent claims, one wins**, repeated 50 times; two concurrent Run nows give one run; duplicate cron delivery; expiry from pending and claimed; claim against expire; **result posted twice writes once**; changed body 409; late result 409; **unknown message ID dropped**; done carried forward, and unticking stops it; `coveredUntil` doesn't advance on failure; user deletion leaves nothing. It sets a fake project ID before `adminDb()` is touched, which `lib/firebase-admin.ts:15` picks up, and **refuses to run unless `FIRESTORE_EMULATOR_HOST` is set**, so it can't reach the shared live project.

**CI** adds a Java setup step and runs a pinned `firebase-tools` with `npx`, so it isn't a project dependency.

**The real app.** `scripts/email-digest-fake-worker.ts` claims, downloads, writes a canned result (including one unknown ID and some hostile markdown) and posts it. No LLM. With it I can drive the dashboard in Chrome on the test account, without the Mac mini. Connecting a Gmail account is a consent click that **you** need to make.
